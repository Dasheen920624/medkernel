# MedKernel 当前架构

## 1. 产品边界

MedKernel 是集团医疗智能中枢，不替代 HIS、EMR、LIS、PACS、护理、手麻、医保等业务系统。
系统保留全部已实现业务页面和接口，并按三个产品空间组织：

| 产品空间 | 主要职责 | 业务域 |
|---|---|---|
| 医疗引擎 | 医疗引擎运营、临床使用 | 工作台、知识治理、临床协同、质量管理 |
| 知识生产 | 医疗引擎运营 | 来源、解析、模型生成、安全门、影子验证、审核、发布 |
| 平台管理 | 平台管理、审计 | 机构与人员、合规安全、系统运维 |

产品空间只负责分区，不隐藏真实能力。页面、路由、菜单和接口的完整清单见
[功能目录](audit/product-function-catalog.md)；S0–S40、全医疗专业领域与统一上线验收范围见
[完整产品范围](PRODUCT_SCOPE.md)。

系统同时交付管理与生产控制台、医疗引擎核心、嵌入组件、API/事件、离线与发布交付物。五种
交付形态共享同一服务层、关系库权威事实、机构生效版本和审计链，不允许页面、CLI、MCP 或
离线工具绕过正式服务直接形成另一套资产与运行状态。

## 2. 六层整体能力模型

诊断、规则或知识生产都不是整套系统的单独中心。完整系统统一由六层能力组成：

| 层级 | 责任 | 主要能力 |
|---|---|---|
| 基础治理层 | 提供可信主体和运行底座 | 机构、组织、人员、四职责、认证、审计、配置、部署、备份恢复 |
| 数据与互操作层 | 把真实院内数据变成可计算事实 | MPI、适配器、FHIR/CDS Hooks、院内主数据、字典映射、13 类标准患者资源、数据质量、幂等与重放 |
| 医疗资产层 | 维护可复用、可验证、可版本化的医学能力 | 来源、知识与说明书、术语、字段目录、值集、公式、规则、路径、评价、随访、安全、医嘱套餐、动作卡 |
| 发布运行层 | 把精确资产版本变成不可变运行事实 | 平台标准版本、机构生效版本、依赖闭包、启停、升级、回滚、离线交付文件 |
| 临床与治理执行层 | 消费患者事实和当前机构生效版本 | 辅助诊疗、推荐诊断、鉴别诊断、检查检验建议、用药安全、路径、报告解读、护理、随访、病历/医保质控、评价整改 |
| 交付与反馈层 | 把能力交付给业务系统并持续改进 | API、嵌入、CLI、MCP、推荐卡、任务、医师确认、反馈、证据、监控和诚实降级 |

S0–S40 是业务场景和专业领域的组合视图，不是 41 套引擎、状态机或数据模型。护理、药事、
急危重症、围手术期、肿瘤、中医药、医技等领域都复用上述六层能力，只维护各自的来源、
术语、知识、规则、路径、指标、随访和动作内容。

组织范围贯穿六层，统一支持平台、集团、医院、院区/成员机构、科室、病区、团队、专科中心、
MDT 和共享中心。组织层级影响数据、资产适用范围与运行启用范围，不派生新角色、新版本体系或
多层交付文件。

## 3. 端到端主链

```text
机构、人员与院内系统
→ 患者主索引、院内主数据和原始业务证据
→ 院内字典映射、单位归一和标准患者资源
→ 来源驱动的知识与结构化医疗资产
→ 平台标准版本与当前机构生效版本
→ 事件触发、规则/路径/知识/评价/随访执行
→ 推荐卡、报告解读、路径节点、质量问题、任务和随访计划
→ 医师确认、反馈、审计、撤回、升级和回滚
```

- 关系数据库是唯一权威业务事实源。
- 临床请求不提交包、领域或资产版本，只提交医院身份、触发点和患者/就诊事实。
- 正式运行只读取当前机构生效版本锁定的精确资产版本。
- 图数据库、搜索、缓存和 Dify 都是可关闭、可重建的投影或执行器。
- 外部依赖不可用时返回真实降级状态，不伪造成功。
- 任何进入诊断、病历、医嘱、支付、上报或设备控制的动作都必须由有权医务人员确认。

## 4. 医疗资产生产与发布

```text
权威来源或机构制度
→ 原件摘要、许可和引用锚点
→ 文档解析或人工维护
→ 模型/模板候选
→ 类型专属结构、引用、红线和测试校验
→ 稳定资产身份下的下一草稿版本
→ 发布为不可变内容版本
→ 平台标准版本或机构生效版本
```

- 大模型只产生候选、草稿或解释，不直接形成临床事实或机构生效版本。
- 知识、规则和路径自动生成复用各自正式维护入口，版本号由服务端自动递增。
- 值集、公式、字段目录、评价、随访、安全、医嘱套餐和动作卡必须具有真实正文、校验和运行消费者；
  只有枚举、模板或哈希不能视为功能完成。
- `PACKAGE` 不是医疗资产，离线交付文件只是平台标准版本或机构生效版本的传输载体。
- `RECOMMENDATION` 不是医疗资产，推荐卡是规则、路径、知识和动作卡执行后产生的运行结果。
- 没有模型时，来源登记、人工维护、确定性校验、发布和全部 B0 临床主链仍可运行。

模型增强通过统一能力网关覆盖来源发现、文档解析、术语映射、规则、路径、诊断、护理、报告、
评价、随访、运营测试和自然语言访问。各能力必须有结构化输出和 B0 路径；模型、Dify、图投影
均不能直接写入正式运行清单。

## 5. 临床与治理能力

### 5.1 辅助诊疗能力层级

辅助诊疗（CDSS）是临床决策支持的上位能力，不是一个仅输出诊断建议的单独步骤。推荐诊断和
鉴别诊断是辅助诊疗中并列、可组合的诊断子能力；两者可以基于同一次患者上下文共同求值，
也可以按触发场景单独运行，不构成必须依次执行的“三层”或三阶段状态机。

除诊断支持外，辅助诊疗还统筹检查检验建议、用药安全、治疗与处置建议、患者路径、风险预警、
护理和连续照护等能力。各子能力共享标准患者事实、当前机构生效版本、来源证据、医师确认和
审计约束，但保持各自清晰的输入、输出与运行消费者。

| 能力 | 真实输入 | 输出与边界 |
|---|---|---|
| 辅助诊疗（上位能力） | 当前患者上下文及当前机构生效版本中的知识、规则、路径和安全资产 | 组合各临床决策支持子能力，形成需医师确认的建议、提醒与任务，不替代医生 |
| 推荐诊断（诊断子能力） | 症状、体征、既往诊断、检验、检查、用药和病史事实 | 候选诊断、置信依据、支持/反驳/缺失证据 |
| 鉴别诊断（诊断子能力） | 候选诊断、患者事实及结构化鉴别知识 | 候选间区分要点、排除/支持证据和下一步检查建议 |
| 检查检验与治疗建议 | 已确认问题、规则、路径、说明书和值集 | 检查、检验、治疗或处置候选，不自动开嘱 |
| 用药安全 | 药品、剂量、途径、过敏、诊断、检验和特殊人群 | 禁忌、相互作用、剂量和监测提醒 |
| 患者路径 | 入径事实、固定路径版本、规则判断和临床时钟 | 候选入径、节点推进、变异、退出和随访接续 |
| 医技报告解读 | 具体患者报告、历史趋势、医技项目说明书和知识 | 异常重点、通俗解释、危急风险和后续建议；不改写原报告 |
| 床旁知识查阅 | 当前权威知识、说明书、指南、制度和来源 | 可追溯检索与解释，不把未发布候选当正式知识 |
| 护理与连续照护 | 护理评估、量表、规则、路径和患者状态 | 护理候选、计划、复评、交班、康复和宣教任务 |
| 随访 | 出院、路径节点、异常结果和随访模板 | 计划、问卷、任务、异常回院和结果回流 |
| 病历/医保/质量评价 | 标准患者资源、规则、指标、公式和值集 | 问题、证据、整改、复核、指标结果和评级材料 |

推荐诊断与鉴别诊断共同构成辅助诊疗中的诊断支持子域，不代表辅助诊疗的全部边界。其关系库
权威、图投影可重建、模型仅做候选/解释、正式运行只读当前机构生效版本等约束，同样适用于
其他临床与治理能力。

## 6. 安全与授权

客户可分配职责固定为平台管理员、医疗引擎运营员、临床使用者、审计员；内置超级管理员
不可手工分配。授权链只有：

```text
固定职责权限包 + 用户组织范围 + 当前请求组织范围
```

不提供租户级角色权限覆盖，不在前端重复检查角色，不通过专业岗位决定系统权限。MFA 默认关闭，
按部署需要开启。详细矩阵见[职责旅程](audit/product-role-journeys.md)。

## 7. 源码分区

| 目录 | 责任 |
|---|---|
| `medkernel-backend/src/main/java/com/medkernel/engine` | 医疗引擎、知识、模型、临床和质量能力 |
| `medkernel-backend/src/main/java/com/medkernel/compliance` | 审计、人员、安全和合规能力 |
| `medkernel-backend/src/main/java/com/medkernel/shared` | 统一契约、配置、安全、审计和可观测性 |

| `frontend/src/shared/config/routes.ts` | 路由、产品空间和入口元数据 |
| `scripts/db` | 单一数据库模式生成器 |
| `deploy` | 容器与单机部署、备份、恢复和回滚 |

## 8. 外部系统与运行约束

所有 HIS/EMR/CDR、LIS、PACS/病理/内镜、药房、护理、手麻、输血、ICU、病案医保、公卫院感、
随访消息、身份源、区域平台、SPD/UDI、科研数据平台和模型 Provider 均通过适配器及标准接入层
进入系统。接入层统一承担签名、幂等、重放、映射、质量、重试、死信、脱敏、审计与断连降级。

FHIR、SMART、CDS Hooks、HL7/CDA、DICOM 与私有接口并存；标准门面不替代院内适配。核心列表
按 10 万级数据设计，写入幂等，正式可用性目标不低于 99.9%，P95/P99 预算由质量门禁和目标
环境演练验证。
