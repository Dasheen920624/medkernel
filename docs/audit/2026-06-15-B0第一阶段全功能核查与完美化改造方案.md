# 2026-06-15 B0 第一阶段全功能核查与完美化改造方案

> 触发：用户明确要求暂停当前推进，先对第一阶段 B0 做一次全功能、全系统、全角色、全链路核查，目标不是进入大模型知识生产，而是确保第一阶段所有人工维护、配置、治理、运行、对接、审计、安全、验收功能足够稳定、合理、可用，避免后续知识或配置建立在有缺陷的基础功能上。

## 0. 结论先行

本次核查不否定第一阶段 B0 全流程结果。第一阶段所称“全流程通过”指的是不引入大模型生产知识的 B0 业务基线、角色旅程和确定性主链路通过。现在要做的是**第一阶段完美化复核**：用更高标准回看所有 B0 功能面，查出先前“能跑通”但还不够合理、不够规模化、不够可维护、不够可交付的地方。

当前结论是：**第一阶段 B0 主链路通过成立，但距离“完美交付”仍有一批必须收敛的问题**。这些问题大多不是阻断 B0 演练的单点故障，而是会影响真实客户长期使用、批量维护、第三方接入、规模数据、角色职责、证据可信度和后续知识生产的地基问题。若不先处理，第二阶段知识生产即使做出来，也可能被第一阶段遗留的字段、版本、权限、审核、路径、对接、性能或体验问题拖垮。

本报告的总裁决：

- **先暂停 wave2 知识生产推进**，不进入 P6，不生产正式知识包。
- **把工作重心切回第一阶段 B0 全功能核查与完美化**。
- **知识治理只是一个重点域，不是全部范围**；还必须覆盖工作台、机构人员、术语、规则、路径、临床协同、随访、质控、配置包、系统接入、审计、安全、运维、沙盘、部署证据和文档真相。
- **所有问题按“会不会导致真实客户用不好、后续知识用不了、证据不可信”来分级**。

## 4. 目标架构

### 4.1 产品面重组

目标是形成两个互相隔离但链路相连的产品面。

| 产品面 | 面向角色 | 目标 | 允许操作 | 禁止操作 |
|---|---|---|---|---|
| 临床/治理运行侧 | 临床治理、质量治理、药事、机构管理员等 | 使用和治理已发布知识 | 查看、审核、发布、替换、恢复、影响分析 | 直接生产平台主源、直接编辑技术 DSL、绕过生产任务 |
| 知识生产侧 | 平台知识治理、医学编辑、领域专家、生产运营、Agent/CLI/MCP 受控身份 | 生产和维护候选资产 | 任务、来源、解析、人工维护、批量导入、候选生成、测试、提交审核 | 直接写运行权威库、跳过审核发布 |

建议路由：

| 路由 | 页面 | 目标 |
|---|---|---|
| `/knowledge-production/workbench` | 生产任务工作台 | job、生产器、进度、失败、重放、中止 |
| `/knowledge-production/sources` | 来源与证据中心 | source、source_version、fragment、引用锚点 |
| `/knowledge-production/assets/diagnosis` | 诊断知识维护 | 诊断身份、标准、鉴别、测试用例、证据 |
| `/knowledge-production/assets/rules` | 规则资产维护 | 规则 DSL 模板、上下文、测试 |
| `/knowledge-production/assets/pathways` | 路径资产维护 | 路径节点、入排/出径、仿真 |
| `/knowledge-production/data-contracts` | 数据契约与字段注册表 | 字段、映射、版本、第三方契约 |
| `/knowledge-production/imports` | 批量导入 | 文件、预校验、错误报告、复核 |
| `/knowledge/governance` | 审核与发布 | 候选审核、差异、证据、影响、发布、驳回 |

### 4.2 资产进入运行库的标准链

```mermaid
flowchart LR
  A["来源登记 source/source_version/fragment"] --> B["生产任务 job"]
  B --> C["候选资产 envelope"]
  C --> D["schema 与类型专属校验"]
  D --> E["人工维护或批量导入补全"]
  E --> F["运行回归测试"]
  F --> G["质量门禁证据"]
  G --> H["审核台会签"]
  H --> I["发布为 asset_version"]
  I --> J["同步 package_version"]
  J --> K["上下文快照运行消费"]
  K --> L["规则/路径/CDSS/诊断/评估/随访"]
```

关键原则：

- 候选可以失败、回滚、重放，但不能直接写权威运行库。
- 发布前必须有真实来源锚点、hash、术语绑定、依赖验证、运行回归。
- packageVersion 只能从系统已登记版本中选择，不能自由输入。
- 每个发布资产都必须能回答：来源是谁、版本是谁、谁生产、谁审核、哪些测试通过、影响哪些运行链、失败如何回滚。

## 5. 重点改造方案

### 5.1 诊断知识

当前诊断知识是本轮最需要优先整改的资产类型，因为它已经有维护界面、运行匹配和发布门禁，但存在“复杂条件可填不可求值”的高风险断层。

改造要求：

1. 将诊断维护迁出 `KnowledgeGovernance`，进入 `/knowledge-production/assets/diagnosis`。
2. 普通维护模式只允许选择医学语义字段，不直接填 `valueConstraint` 字符串。
3. 诊断标准结构改为：
   - `findingCode`：标准术语编码，强制绑定术语版本。
   - `predicate`：存在、等于、区间、趋势、变化率、异常标志等结构化算子。
   - `value`：数值、文本、编码、枚举。
   - `unit`：标准单位和换算规则。
   - `timeWindow`：发生时间、持续时间、最近一次、趋势窗口。
   - `sourceQuality`：数据来源、可信级、是否人工确认。
   - `citationRef`：当前版本内的来源锚点。
4. 发布门禁：
   - 若包含系统尚不支持的 predicate，直接阻断发布。
   - 每条 required/exclusion 标准至少有一个阳性或阴性测试覆盖。
   - 每个鉴别诊断至少有差异点和测试用例。
   - 复杂诊断必须跑真实上下文 fixture，而不是逗号 findings。
5. 修复 `parseFindings` 重复项异常，所有旧测试用例迁移为结构化 fixture。
6. 批量导入支持 CSV/JSONL/Excel，但必须先生成错误行报告，不允许边导边发布。

### 5.2 路径入排与上下文字段

当前路径 include/exclude 不是完全无效，后端确实有求值逻辑。真正问题是 UI 选择的 canonical 字段路径与运行时 `criteriaContext` 生成的事实路径不完全一致，导致用户感觉“配置了但没效果”。

改造要求：

1. 建 `ContextFactBridge`：
   - 输入：ContextSnapshotResources、字段目录 path、packageVersion。
   - 输出：统一 JsonNode，包含 canonical arrays 和按 code 索引的便捷路径。
   - 保证 `observations[].valueNumeric`、`observation.HB.valueNumeric` 等路径可被一致解释。
2. 字段目录每个字段必须有“运行支持状态”：
   - `SUPPORTED`：可用于规则/路径/CDSS/诊断。
   - `MAPPED_ONLY`：可入契约，但运行需转换。
   - `UNSUPPORTED`：仅展示或待接入，不能用于发布门禁。
3. 路径发布门禁：
   - 入径纳入、入径排除、出径纳入、出径排除分别用真实上下文 fixture 测试。
   - 每个条件组至少有一个命中和一个不命中样例。
   - 使用 unsupported 字段时阻断发布。
4. 前端预览必须显示：
   - 当前字段来源。
   - 实际运行路径。
   - 最近一次模拟命中结果。
   - 未命中原因。

### 5.3 字段目录升级为数据契约中心

字段目录不应只是“上下文字段目录维护”。它应成为知识生产、规则、路径、CDSS、第三方接入的共同契约。

新增字段模型建议：

| 字段 | 说明 |
|---|---|
| `canonicalPath` | 平台标准字段路径 |
| `displayName` | 中文展示名 |
| `resourceType` | Patient/Observation/Condition/Medication/Order 等 |
| `dataType` | number/string/code/date/list/object |
| `cardinality` | 0..1、1..1、0..*、1..* |
| `requiredPolicy` | 必填、运行必需、可空、条件必填 |
| `nullPolicy` | 缺失、未知、未采集、不可用如何处理 |
| `unit` | 标准单位 |
| `unitConversion` | 单位换算策略 |
| `valueSet` | 字典或值域绑定 |
| `codeSystem` | ICD/LOINC/本位码/院内码等 |
| `fhirPath` | FHIR 映射 |
| `sourceSystem` | HIS/EMR/LIS/PACS/手麻/输血/医保等 |
| `adapterMapping` | 第三方字段映射 |
| `phiLevel` | PHI/敏感级 |
| `dataLevel` | D0-D5 |
| `supportedEngines` | rule/pathway/cdss/diagnosis/evaluation/followup |
| `packageVersion` | 生效包版本 |
| `compatibility` | 兼容、弃用、替代字段 |
| `samplePayload` | 样例 |
| `validationRules` | 校验规则 |

### 5.4 第三方与批量导入

第三方接入不应只下载字段清单。必须给出可执行契约和校验结果。

目标能力：

- OpenAPI 文档。
- JSON Schema。
- CSV/JSONL/Excel 模板。
- 字段映射表。
- 单位和值域说明。
- 必填和空值策略。
- 示例 payload。
- 预校验接口。
- 导入 job。
- 错误行报告。
- 幂等键。
- 死信和重放。
- 审计和签名。
- 断连降级状态。

第三方知识生产或批量新增入口统一走：

```mermaid
flowchart LR
  A["第三方/CLI/MCP/Agent"] --> B["签名与权限"]
  B --> C["生产任务 job"]
  C --> D["Envelope schema 校验"]
  D --> E["类型专属校验"]
  E --> F["预校验报告"]
  F --> G["人工复核"]
  G --> H["候选进入审核台"]
```

不得允许第三方直接写诊断表、规则表、路径表或权威版本表。

### 5.5 版本与发布治理

改造要求：

1. packageVersion 不允许自由输入，必须从版本选择器选择。
2. 版本选择器显示：
   - 包编码。
   - 版本号。
   - 状态。
   - 生效范围。
   - 来源基线。
   - 是否弃用。
   - 兼容版本。
   - 最近同步时间。
3. 诊断、规则、路径、字段目录、第三方契约必须显式绑定 packageVersion。
4. 发布前展示版本关系：
   - 来源版本。
   - 资产版本。
   - 审核批次。
   - 包版本。
   - 运行快照。
5. 换基线和覆盖：
   - 平台主源不可被机构反写。
   - 院内覆盖必须记录派生来源。
   - 恢复平台标准必须可回滚。

### 5.6 审核台与质量门禁

审核台目标不是“填表发布”，而是让审核者快速判断候选是否可以进入运行权威链。

审核台必须展示：

- 候选内容与当前生效版本的差异。
- 来源锚点和原文片段。
- 术语绑定率。
- 依赖完整性。
- 运行回归结果。
- 影响模拟。
- 高风险标记。
- 需要会签的角色。
- 例外理由。
- 回滚方案。

质量门禁应由系统生成：

| 门禁 | 系统证据 | 人工动作 |
|---|---|---|
| 结构校验 | schema 校验报告 | 只能查看 |
| 术语绑定 | 术语版本和覆盖率 | 修正或申请例外 |
| 来源锚点 | hash、source_version、fragment | 确认引用合理 |
| 依赖完整 | 规则/路径/CDSS/知识引用存在 | 修复依赖 |
| 运行回归 | fixture 结果 | 复核失败 |
| 影响模拟 | 命中差异和受影响机构 | 确认发布 |
| 同行复核 | 审核记录 | 签字 |
| 高风险双签 | 双人电子签名 | 签字 |
