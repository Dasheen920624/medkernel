## 1. 产品定位

MedKernel 是集团医疗智能中枢。它把院内真实数据、标准术语、权威知识、规则、路径、评价、
随访和临床安全资产连接起来，在医院当前运行修订下执行确定性计算与可选模型增强，向临床、
护理、药事、医技、质量、医保和管理场景输出可解释、可确认、可追溯的建议与任务。

MedKernel 不替代 HIS、EMR、LIS、PACS、病理、护理、手麻、输血、药房、医保、病案、公卫、
科研或区域平台。源系统继续负责原始业务记录、报告签发、医嘱执行、病历归档、支付、上报和
设备控制；MedKernel 负责标准化、计算、建议、协同、反馈和证据闭环。

完整上线不是“有页面、有表、有枚举”，而是以下主链能够使用真实数据端到端运行：

```text
机构与人员
→ 院内系统和患者真实数据
→ 院内字典与标准术语映射
→ 标准患者资源与字段目录
→ 来源、知识、说明书和值集等医疗资产
→ 规则、路径、评价、随访和安全资产
→ 平台权威基线与医院当前运行修订
→ 临床、护理、药事、医技和质量运行
→ 建议、任务、确认、反馈、审计、撤回和回滚
```

## 2. 文档权威与概念边界

权威顺序为：

```text
CONSTITUTION
→ PRODUCT_SCOPE
→ ARCHITECTURE / EXPERIENCE_CONTRACT
→ 功能目录 / 职责矩阵 / 数据库 / 质量基线
→ 代码与自动化契约
→ _HANDOFF 当前施工状态
```

必须区分以下概念：

- S0–S40 是业务场景组合，不是 41 套引擎；
- 全医疗专业领域是内容和适用范围，不是独立数据模型、角色体系或发布体系；
- 11 个知识内容分类用于检索与治理，不是全部医疗专业领域或医学语义边界；
- 13 类版本化资产是统一治理对象，不等于 13 个页面；
- 平台基线和医院运行修订是不可变运行清单，不是可变“包指针”；
- 发布制品只负责传输和校验，不是医疗资产，也不承载独立业务版本；
- 推荐卡、患者路径实例、报告解读、质量问题和随访计划是运行结果，不是配置资产。

## 3. 六层完整能力模型

| 层级 | 责任 | 完整上线能力 |
|---|---|---|
| 基础治理 | 建立可信主体和运行底座 | 服务机构、组织、任职、账号、四职责、认证、MFA 开关、审计、配置、部署、备份恢复 |
| 数据与互操作 | 把真实院内数据变为可计算事实 | MPI、系统接入、签名验真、幂等、重放、院内主数据、字典映射、单位归一、13 类标准患者资源、数据质量 |
| 医疗资产 | 维护可复用的医学能力 | 来源、知识、说明书、术语、字段目录、值集、公式、规则、路径、评价、随访、安全、医嘱套餐、动作卡 |
| 发布运行 | 将精确资产版本变为不可变运行事实 | 平台权威基线、医院扩展、医院当前运行修订、依赖闭包、部分选择、升级、回滚、离线制品 |
| 临床与治理执行 | 消费患者事实和当前运行修订 | 辅助诊疗、诊断支持、检查检验、用药安全、路径、报告解读、护理、随访、病历/医保质控、评价整改 |
| 交付与反馈 | 把结果送达业务现场并持续改进 | API、嵌入、CLI、MCP、推荐卡、任务、医师确认、反馈、证据、监控、诚实降级 |

任何功能必须能说明自己属于哪一层、消费什么真实输入、使用哪类精确资产版本、产生什么结果、
由谁确认、如何审计以及依赖不可用时如何降级。

### 3.1 五种完整交付形态

同一中枢能力必须以五种形态交付，不能只完成管理页面或单个 API：

| 交付形态 | 主要使用方 | 必须交付 |
|---|---|---|
| 管理与生产控制台 | 平台、医院信息科、医务、质控及资产运营人员 | 机构接入、知识生产、字典、规则、路径、发布运行、质量、安全和运维页面 |
| 医疗引擎核心 | 院内部署与业务服务 | 标准化、资产解析、规则/路径/评价/随访执行、诊断支持、证据和诚实降级 |
| 嵌入组件 | 医生站、护士站、质控系统和院内门户 | 提醒卡、路径节点、待办、解释、反馈及可信启动组件 |
| API 与事件 | HIS、EMR、CDR、LIS、PACS 等院内外系统 | REST、Webhook、FHIR/CDS Hooks 风格门面、批量、消息和回调契约 |
| 离线与发布交付物 | 外网平台、院内离线环境和实施运维 | 平台基线/医院运行修订制品、数据库基线、部署包、备份恢复和验收工具 |

五种形态共享同一关系库权威模型、权限、运行修订、审计和错误语义，不允许各自维护一套业务
状态、资产版本或患者事实。

## 4. 组织、权限与人员模型

客户可分配职责固定为四个：

| 职责 | 主要范围 |
|---|---|
| 平台管理员 | 服务机构、组织、人员账号、身份来源、系统接入和平台配置 |
| 医疗引擎运营员 | 来源、知识、术语、规则、路径、模型生产、发布运行和质量配置 |
| 临床使用者 | 患者、推荐、路径实例、任务、随访、确认和反馈 |
| 审计员 | 审计、证据、质量与运行合规的只读核查 |

内置超级管理员只用于首次接管和应急，不可日常分配。医生、护士、药师、医技人员、质控人员、
医保人员等是业务任职和组织范围，不新增系统角色。最终授权只有：

```text
固定职责权限包 + 用户组织范围 + 当前请求组织范围
```

不允许租户自定义角色权限覆盖、专家委员会门槛、双人会签、职责分离等待链或按专业岗位复制
权限体系。MFA 默认关闭，部署方按需开启；开启后必须执行真实 TOTP 登录验证。

### 4.1 集团组织与业务任职

系统原生承载以下组织拓扑：

```text
平台
└─ 集团
   ├─ 医院
   │  ├─ 院区 / 分院
   │  │  ├─ 社区卫生服务中心 / 基层成员机构
   │  │  └─ 科室 → 病区 → 医疗/护理团队
   │  └─ 专科中心 / MDT / 专病团队
   └─ 共享中心：知识、质控、医保、信息、合规
```

组织层级只决定数据范围、资产适用范围、运行启用范围和责任归属，不产生新的系统角色或多层包。
医生、护士、药师、技师、编码员等通过任职、资质、科室、团队和组织范围表达；同一人员可在
不同机构或组织拥有不同任职，但系统权限仍只来自四个固定职责。

## 5. 数据与互操作模型

### 5.1 真实数据入口

支持 HIS、EMR、LIS、PACS、病理、护理、手麻、输血、药房、医保、病案、随访、公卫、科研和
区域平台通过 REST、Webhook、FHIR/CDS Hooks 风格门面、HL7/CDA、消息、文件、中间库或视图
接入。所有入口统一经过：

```text
接入系统身份
→ 签名、时效和重放校验
→ 幂等接收与原始证据摘要
→ 字段映射、术语映射和单位归一
→ 标准患者资源
→ 临床事件与上下文快照
→ 当前医院运行修订解析
→ 对应运行消费者
```

临床调用方只提交机构、触发场景和患者/就诊事实，不提交发布制品、领域、资产版本或运行版本。

### 5.2 标准患者资源

患者事实统一落入 13 类标准资源：

1. Patient；
2. AllergyIntolerance；
3. Encounter；
4. Condition；
5. NursingAssessment；
6. Observation；
7. DiagnosticReport；
8. Medication；
9. Procedure；
10. Document；
11. CarePlan；
12. FollowUp；
13. Claim。

每个资源必须保留租户、组织、患者、就诊、来源系统、来源标识、业务时间、接收时间、数据质量、
原始证据摘要和映射版本。字段目录中的非派生路径必须落到真实资源字段；派生字段必须有确定性
求值器、输入依赖、单位和缺失策略。

### 5.3 院内字典到运行资产

```text
院内主数据/码表
→ 院内术语
→ 标准术语候选
→ 冲突与高危近似检测
→ 当前责任人确认
→ 不可变映射版本
→ 标准患者资源
→ 值集、规则、路径、评价、知识说明书
→ 医院运行修订
```

诊断、药品、检验、检查、手术、耗材、医嘱、科室、文书和随访项均使用同一映射机制。高危近似
映射禁止自动确认和批量确认。

## 6. 医疗资产统一模型

### 6.1 稳定身份与自动版本

每项资产由稳定身份和不可变内容版本组成：

```text
稳定资产身份
→ V1 已发布
→ 基于 V1 创建下一草稿
→ 服务端自动分配 V2
→ 校验并发布 V2
→ 历史运行继续引用 V1，新运行修订可选择 V2
```

维护者不手工填写版本号。删除、撤回或退回草稿不会改写历史版本；下一医院运行修订决定该资产
是否继续进入新运行。历史运行修订及证据始终可重放。

### 6.2 可发布资产类型

最终可进入发布清单的资产固定为 13 类：

| 类型 | 真实内容 |
|---|---|
| KNOWLEDGE | 医学正文、适用范围、来源引用、风险和解释 |
| TERMINOLOGY | 标准术语、院内映射、有效期和确认记录 |
| RULE | 触发、完整条件树、缺失策略、动作、解释和测试向量 |
| PATHWAY | 准入、节点、边、时钟、变异、退出和随访接续 |
| EVALUATION | 分母、分子、排除、评分、周期和证据定位 |
| FOLLOWUP | 目标人群、周期、问卷、异常动作和回院指针 |
| FIELD_CATALOG | 字段路径、类型、基数、单位、值域和隐私级别 |
| SAFETY | 禁忌、红线、风险级别、确认要求和撤回传播 |
| CDSS_RISK | 打扰等级、风险矩阵、疲劳控制和升级策略 |
| VALUE_SET | 稳定值集、编码体系、成员、有效期和版本 |
| FORMULA | 输入字段、单位、表达式、阈值和测试向量 |
| ORDER_SET | 医嘱候选项、顺序、依赖、禁忌和确认要求 |
| ACTION_CARD | 建议、证据、可选动作、确认和反馈契约 |

`PACKAGE` 不是医疗资产；`RECOMMENDATION` 不是配置资产。任何类型只有具备真实内容存储、类型
校验、精确依赖、发布快照、运行消费者、离线迁移和回滚后，才算完整功能。

### 6.3 知识内容分类

11 个知识域只用于分类可发布的医学内容：

1. 指南共识 `GUIDELINE`；
2. 药品说明书 `DRUG`；
3. 路径性知识 `PATHWAY_KNOWLEDGE`；
4. 护理知识 `NURSING`；
5. 医技项目说明书 `DIAGNOSTIC_ITEM`；
6. 中医药 `TCM`；
7. 院内制度 `PROTOCOL`；
8. 政策 `POLICY`；
9. 学术文献 `LITERATURE`；
10. 诊断知识 `DIAGNOSIS`；
11. 其他知识 `OTHER`。

医技项目说明书描述项目定义、适应证、准备、参考范围、局限和意义；患者报告解读消费具体患者
报告和说明书，是独立运行功能，不写回知识正文。

### 6.4 规则与路径纯粹性

- 一条规则自包含完整条件树、动作、解释和测试，不引用条件片段库；
- 一条路径自包含节点、边、时钟、变异和退出，不引用子路径、不继承其他路径；
- 规则之间、路径之间不允许循环嵌套；
- 路径边可以单向调用医院当前运行修订锁定的规则进行分支判断；
- 路径调用规则不是条件片段或子路径；
- 后续复用通过“复制规则”或“复制路径”产生新的稳定身份，不建立共享嵌套资产。

## 7. 平台、机构、发布与运行

### 7.1 四个不同对象

| 对象 | 含义 |
|---|---|
| 平台权威基线 | 平台主源发布的一组精确资产版本，不可变、可追溯 |
| 机构扩展 | 某机构对平台稳定身份的同源覆盖，或只归本机构的新增资产 |
| 医院运行修订 | 某医院一次实际启用的完整精确资产清单，不可变 |
| 发布制品 | 基线或运行修订的离线传输文件，仅负责完整性、签名和导入 |

平台权威基线唯一。每家医院可以有不同的运行修订序列，修订使用全局标识和来源坐标，不与平台
版本号竞争，因此医院本地迭代不会与后续平台升级发生编号冲突。

### 7.2 医院有效内容

医院创建运行修订时按稳定资产身份解析：

```text
所选平台权威基线
+ 已选择启用的机构同源覆盖
+ 已选择启用的机构新增资产
- 已明确停用的资产
= 医院运行修订的完整精确版本清单
```

医院可按专业领域、业务场景、路径、规则、知识、组织范围或任意选择集分批上线，不强制整套启用。
选择结果必须完成依赖闭包校验：缺少字段、术语、值集、规则、知识或安全资产时禁止激活。

平台升级时生成新的平台权威基线。医院先做差异、冲突和影响分析，再创建新的医院运行修订；
不会原地修改当前运行修订，也不会遗漏未变化资产。离线导出默认是所选基线或运行修订的完整
精确快照，不依赖接收端已有增量历史。

### 7.3 运行解析

每个医院同一时间只有一个当前运行修订。临床事件接收时由服务端锁定该修订，规则、路径、知识、
评价、随访和安全消费者均从修订中解析精确版本。后续发布不会改变已形成的事件快照和运行证据。

## 8. 医疗资产生产与大模型

支持三种生产入口：

1. 人工维护；
2. 权威来源解析和结构化生成；
3. 大模型自动生成候选。

统一流程为：

```text
来源登记与原件摘要
→ 解析和引用锚点
→ 新增/新版/重复/冲突识别
→ 模型或模板候选
→ 类型专属结构校验
→ 医学回归、红线和测试向量
→ 稳定身份下的下一草稿版本
→ 当前责任人审核与发布
→ 平台基线或医院运行修订
```

大模型可以生成知识、规则、路径及其他结构化资产候选，但必须遵循对应正式 schema、依赖和版本
入口。模型不手工指定 V1/V2/V3，不直接发布，不直接形成诊断、医嘱、病历或患者事实。关闭模型
后，来源登记、人工维护、确定性校验、发布和 B0 运行主链必须完整可用。

关系数据库保存权威资产和关系；图数据库只保存可重建投影，用于诊断标准、鉴别关系、诊疗指针、
来源关系和解释查询。图不可用不得阻断权威维护和确定性运行。

### 8.1 全中枢模型赋能矩阵

模型通过统一能力网关增强全中枢，而不是只服务知识正文或诊断：

| 能力面 | 模型增强 | B0 确定性/人工主链 | 正式生效边界 |
|---|---|---|---|
| 来源发现 | 公开权威来源发现、更新提示、差异摘要 | 人工登记、许可和时效核验 | 未核验来源不能进入正式资产 |
| 文档与说明书 | OCR、章节识别、字段抽取、引用定位 | 人工录入、模板解析和引用校验 | 原件摘要与引用锚点必须保留 |
| 术语与字典 | 同义词、标准码和冲突候选 | 导入、精确匹配、人工确认 | 高危近似禁止自动确认 |
| 规则与质量 | 条件树、解释、测试向量和指标候选 | 可视化/DSL 编辑、确定性校验和仿真 | 模型结果只能进入草稿 |
| 路径与连续照护 | 节点、分支、时钟、变异和随访候选 | 路径画布、规则判断、时钟执行 | 不自动入径或推进患者 |
| 诊断与辅助诊疗 | 候选、证据归纳、鉴别和解释 | 已发布知识、规则、图投影回退 | 不替代医师诊断和医嘱 |
| 护理与专科协同 | 评估、计划、交班和协同摘要候选 | 量表、规则、路径和人工维护 | 由有资质人员确认 |
| 医技报告 | 摘要、趋势、通俗解释和复核候选 | 结构化结果、阈值、规则和说明书 | 不改写已签发报告 |
| 评价、医保与病案 | 问题归因、整改说明和材料摘要 | 公式、值集、规则和证据定位 | 不自动形成支付或法定结论 |
| 随访与宣教 | 问卷、宣教、异常说明和计划候选 | 固定模板、规则、路径和任务引擎 | 不在中枢内替代呼叫中心 |
| 运营与测试 | 影响分析、测试候选和异常归纳 | 固定回归集、门禁和监控 | 不得用生成结果伪造验收 |

任何模型任务都必须声明能力代码、组织范围、数据级别、来源约束、输出 schema、超时、降级策略和
审计字段。Provider、图、Dify 或网络不可用时，对应行的 B0 主链仍须可用。

## 9. 临床与治理执行能力

### 9.1 辅助诊疗层级

辅助诊疗（CDSS）是上位能力，统筹诊断支持、检查检验建议、用药安全、治疗与处置建议、患者
路径、风险预警、护理和连续照护等能力。

推荐诊断与鉴别诊断是其中并列、可组合的诊断子能力：

- 推荐诊断产生候选诊断、置信依据和支持/反驳/缺失证据；
- 鉴别诊断比较候选，产生区分要点、排除/支持证据和下一步检查建议；
- 两者可以共同求值或按场景独立运行，不构成三层或三阶段状态机。

### 9.2 主要运行输出

| 能力 | 真实输入 | 运行输出 |
|---|---|---|
| 诊断支持 | 患者事实、诊断知识、规则、鉴别关系 | 候选诊断、鉴别要点、诊疗指针和推荐卡 |
| 检查检验建议 | 当前问题、项目说明书、规则、路径和值集 | 检查/检验候选、准备要求、重复检查提示 |
| 用药安全 | 药品、剂量、途径、过敏、诊断、检验和特殊人群 | 禁忌、相互作用、剂量和监测提醒 |
| 治疗与处置建议 | 已确认问题、路径、规则、安全和医嘱套餐 | 治疗、处置或会诊候选，不自动开嘱 |
| 患者路径 | 入径事实、固定路径版本、规则判断和临床时钟 | 候选入径、节点推进、变异、退出和随访接续 |
| 医技报告解读 | 患者报告、历史趋势、项目说明书和知识 | 异常重点、趋势、危急风险和后续建议，不改原报告 |
| 床旁知识 | 当前权威知识、说明书、指南、制度和来源 | 可追溯检索、条款定位和解释 |
| 护理与连续照护 | 护理评估、量表、规则、路径和患者状态 | 分级候选、计划、复评、交班、康复和宣教任务 |
| 随访 | 出院、路径节点、异常结果和随访资产 | 计划、问卷、任务、异常回院和结果回流 |
| 病历/医保/质量 | 标准患者资源、规则、指标、公式和值集 | 问题、证据、整改、复核、指标结果和评级材料 |

所有临床输出必须显示来源、资产版本、患者快照、风险、生成方式和确认状态。任何建议进入病历、
医嘱、支付、上报、签署或设备控制前必须由有权医务人员确认。

### 9.4 专病路径全周期

每条专病或专业路径必须显式覆盖以下十个阶段；不适用时记录原因，不能无声缺失：

```text
筛查与分诊
→ 诊断与鉴别
→ 风险分层
→ 治疗决策
→ 医疗/护理执行候选
→ 监测与预警
→ 出院与转诊
→ 康复、宣教与随访
→ 结局评价
→ 质量改进与资产迭代
```

路径本身只编排节点、时钟、变异和规则判断，不复制规则内容，也不控制医嘱、设备或法定上报。

### 12.1 七类业务服务组合

客户项目可以按下列组合采购、实施或验收，但它们只是六层公共能力的视图，不是版本包、独立
引擎、独立状态机或独立权限体系：

| 服务组合 | 组合能力 |
|---|---|
| 机构开通与接入 | 组织、任职、系统接入、主数据、字典映射、数据质量和运行准备 |
| 临床运行 | 患者事实、诊断支持、规则、路径、推荐卡、嵌入、反馈和随访 |
| 质量改进 | 病历、病案、医保、指标评价、问题、整改、复核和价值指标 |
| 合规与运维 | 身份、安全、审计、配置、监控、备份恢复、国产化和证据 |
| 第三方接口 | 适配器、FHIR/CDS Hooks 门面、Webhook、消息、批量、回调和补偿 |
| 专病路径 | 专病来源、术语、知识、规则、路径、关键时钟、指标和随访 |
| 专业协同 | 护理、药事、医技、MDT、感控、公卫、综合照护、科研和区域协同 |

每个组合必须列出角色映射、真实数据、资产依赖、运行输出、接口/页面承载、降级、安全边界和
验收用例。组合不能成为再次制造冗余页面或容器版本的理由。

## 13. 交付、反馈与运行降级

所有临床和治理结果至少支持 API；需要进入工作站的能力支持 iframe、Web Component、JS SDK
或受信启动页中的一种。CLI 和 MCP 只复用正式后端服务，不建立旁路数据模型或权限。

运行结果必须包含：

- 组织、患者/对象、触发场景和时间；
- 医院运行修订；
- 实际使用的资产身份、版本和内容摘要；
- 输入快照与质量状态；
- 输出、风险、解释和来源；
- AI/B0 标识；
- 确认、反馈、覆盖理由和审计。

模型、图、缓存或外部系统不可用时必须返回真实的 `MODEL_DISABLED`、`NOT_CONNECTED`、
`NOT_SYNCED` 或 B0 状态。同步超时不得阻断医生主流程，不允许吞错后伪造成功。

### 13.1 第三方系统全景

| 系统族 | 主要方向 | 中枢责任 |
|---|---|---|
| HIS、EMR、CDR、医嘱与费用 | 双向 | 患者上下文、事件、提醒、质控、路径节点和反馈 |
| LIS、监护与危急值 | 输入为主、闭环回传 | 结果标准化、趋势、预警、处置任务和证据 |
| PACS/RIS、超声、病理、内镜、心电 | 输入为主、闭环回传 | 报告资源、说明书关联、解读、复核和危急闭环 |
| 药房、审方和药事平台 | 双向 | 药品映射、用药安全、监测、点评和整改 |
| 护理、手麻、手术室、输血和 ICU | 双向或输入为主 | 专业事件、风险、路径、核查、任务和确认回传 |
| 病案、医保和支付 | 双向或输出为主 | 编码/费用问题、规则证据、人工确认和结果回流 |
| 公卫、院感、不良事件和监管 | 双向 | 预填、风险、任务、人工上报和审计，不代替法定系统 |
| 随访、消息和患者服务 | 双向 | 计划、问卷、异常、回院指针和执行结果 |
| CA、OIDC、SSO、HR/OA | 输入为主 | 身份来源、任职同步、可信启动和账号生命周期 |
| 区域平台、医联体和远程协同 | 双向 | 互认、转诊、跨院路径、来源和协同任务 |
| SPD、UDI、器械耗材 | 输入为主 | 术语、适用性、召回停用、技术准入和风险提醒 |
| 科研、伦理和数据平台 | 输出为主、审批回传 | 脱敏队列、指标、授权、导出和使用审计 |
| 模型 Provider、Dify 和 Agent | 受控输入输出 | 候选、解释和任务执行；不得成为权威业务源 |

所有对接点必须提供字段/术语映射、签名、幂等、时效、重放、健康检查、重试死信、数据质量、
脱敏、审计和断连降级。不得控制医疗设备或自动完成医嘱、输血、手术、支付、签署、归档和法定
上报。

### 13.2 非功能、监管与中国医院落地

- 标准兼容：FHIR、SMART、CDS Hooks、HL7 v2/CDA、DICOM 及院内私有适配并存，标准门面不要求
  医院一次性改造全部源系统；
- 数据主权：患者数据、权威资产、版本、审核结论和运行结果以院内关系数据库为准；外部生产中心
  只处理已授权公开来源，患者明文不得外流；
- 合规边界：落实个人信息保护、网络安全、数据安全、等保、商用密码和生成式 AI 相关要求，
  具体等级与备案由部署机构依法确认；
- 国产化：PostgreSQL、Kingbase、Oracle、达梦和 H2 来自同一模式源，部署支持国产操作系统、
  中间件和离线环境的实际验证；
- 性能：核心交互设定并验证 P95/P99 预算；知识、日志、患者和证据等 10 万级列表必须服务端分页、
  游标或异步导出；
- 可用性：正式目标可用性不低于 99.9%，关键写入幂等，重试不会产生重复临床结果；
- 评级支撑：可输出电子病历评级、互联互通、数据质量和闭环证据，但不承诺医院整体评级结果；
- 价值度量：至少覆盖提醒有效率、采纳/拒绝、路径执行、异常闭环、随访完成、整改关闭、数据质量
  和运行稳定性，禁止只展示无行动入口的装饰性指标。

## 15. 完整上线验收

上线必须同时证明：

1. 六层能力均有真实存储、服务、权限、消费者和审计；
2. 13 类标准患者资源可由真实接入落地并驱动运行；
3. 13 类版本化资产均有真实正文、校验、依赖、发布和运行消费者；
4. 11 个知识内容分类均能从权威来源生产、审核、发布、替换和回滚；
5. 全医疗专业领域至少各有一组权威代表资产完成生产、发布、运行和证据闭环；
6. S0–S40 按公共引擎组合完成正常、异常、缺数、高风险和降级演练；
7. 平台基线、两家机构差异化扩展、部分选择上线、升级和回滚可重放；
8. 临床调用方不传发布制品、领域或版本，服务端始终解析医院当前运行修订；
9. 四职责覆盖全部菜单和运行端点，MFA 默认关闭并可真实开启；
10. 模型自动生成知识和结构资产候选可用，关闭模型后 B0 主链仍完整；
11. 五数据库方言由一个模式源生成同版本迁移并通过支持范围验证；
12. 五种交付形态、七类业务组合和全部第三方系统族均有真实消费者与断连降级验证；
13. 集团—医院—院区/成员机构—科室/病区/团队组织范围和跨机构任职得到验证；
14. 完整医疗语义、专病十阶段和全中枢模型赋能矩阵均有代表性权威资产和 B0 用例；
15. 目标环境完成备份恢复、清库 V1、部署、全功能全知识演练、重启和再次恢复验证。

## 16. 明确删除或禁止的复杂度

- 条件片段库、子路径、路径继承和循环嵌套；
- 租户自定义角色权限覆盖、冗余角色和前端角色硬编码；
- 高风险双签、专家委员会、独立专家签字和不可落实的职责分离等待链；
- MFA 默认强制或按角色维护强制名单；
- 临床请求传入发布制品、领域、资产版本或运行版本；
- 把发布制品、推荐结果、报告解读或患者路径实例当成医疗资产；
- 五套手写数据库迁移；
- 未发布候选参与临床运行；
- 图数据库、Dify、缓存或模型成为业务权威源；
- 旧迁移、旧兼容入口、历史截图和重复阶段文档。

## 17. AI 接力检查

任何 AI 开始工作时：

1. 先读 `_HANDOFF.md` 确认分支、当前任务和外部事实；
2. 再按本文件第 2 节的权威顺序读取与任务直接相关的最少文档；
3. 用代码、测试和生成产物核实现状，不根据旧文档或会话记忆臆测；
4. 不把用户举例缩成全部产品范围，也不因整理架构删除现有真实功能；
5. 需求或架构裁决变化时，同步更新本文、相关架构/契约和 `_HANDOFF.md`；
6. 完成声明必须给出与本文件第 15 节逐项对应的证据。
