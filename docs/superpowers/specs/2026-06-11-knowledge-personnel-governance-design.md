# 医疗知识与人员身份治理重构设计

## 1. 决策摘要

本次重构以平台为唯一主源、客户机构按需定制为知识治理主线，以自然人、任职、账号、身份来源相互分离为人员治理主线。项目尚未上线，不保留低质量交互和错误概念的兼容层。

核心决策：

1. `t-1` 是平台主租户，不是客户组织树中的上级机构；`PLATFORM` 是平台治理层，客户租户下才建立集团、医院、院区、基层医疗卫生机构、科室和病区。
2. 平台医疗知识默认引用复用，不物理复制到客户主源；客户明确发起定制时，创建同一业务键的本地派生版本，并保存平台身份、平台基线版本和目标组织范围血缘。
3. 人是权威主体，任职描述人在什么机构以什么身份工作，账号只负责登录，外部身份只负责认证映射，角色授权绑定任职和组织范围。
4. 用户管理升级为“人员与账号”，身份绑定升级为“身份来源”，组织范围全部通过组织树选择，不允许客户直接维护 `TENANT`、`HOSPITAL`、`t-1` 等技术编码。
5. 批量流程采用“上传文件 → 字段识别 → 数据校验 → 匹配去重 → 冲突处置 → 预览提交 → 结果回执”的可恢复任务，不逐条创建。
6. 客户可见页面只显示中文业务名称；英文枚举保留为接口和数据库稳定编码，不直接暴露。
7. 删除早期固定岗位角色矩阵，采用“职责角色 + 任职岗位 + 组织范围”三分法；旧角色编码不再识别、不做别名兼容，清库后只初始化新角色。

## 2. 领域模型

### 2.1 平台与组织

稳定层级：

| 技术层级 | 客户名称 | 说明 |
|---|---|---|
| `PLATFORM` | 平台治理层 | 仅平台运营、全局知识和标准包治理 |
| `TENANT` | 客户机构 | 数据隔离根，可代表集团、单体医院或服务机构 |
| `REGION` | 集团/医联体 | 客户内部的集团化或区域协同层 |
| `FACILITY` | 医疗服务机构 | 医院、独立分院、社区卫生服务中心、乡镇卫生院、村卫生室等 |
| `CAMPUS` | 院区/服务点 | 同一机构下的院区、门诊部或服务站点 |
| `DEPARTMENT` | 科室/业务部门 | 临床、医技、行政或公共卫生部门 |
| `WARD` | 病区/护理单元 | 科室下的住院或护理单元 |

独立法人、独立运营或独立数据责任边界的分院建为 `FACILITY`；同一医院的不同地理运营地点建为 `CAMPUS`。机构类型是 `FACILITY` 的属性，不增加新的树层级。

### 2.2 人员主数据

#### 人员 `person`

表示唯一自然人，保存租户内人员标识、姓名、人员状态和必要的脱敏联系方式。人员不等于账号，一个人可以没有账号，也可以关联多个认证来源。

#### 任职 `person_appointment`

表示人员在某组织中的工作关系：

- 所属机构和科室
- 人员类别：院内员工、集团共享人员、外部协作人员、供应商实施人员
- 岗位/职称
- 主任职或兼岗
- 生效和失效时间
- 在职、待入职、停用、离职状态

一个人员可有多个任职，但同一时间只能有一个主任职。调岗通过结束旧任职、新建新任职完成，保留历史。

#### 职责角色

职责角色只表达“可以承担什么系统责任”，不再重复表达人员在哪一级机构、是什么岗位：

| 角色编码 | 客户名称 | 责任边界 |
|---|---|---|
| `platform-governance-admin` | 平台治理管理员 | 平台、客户空间、全局配置和授权治理 |
| `platform-knowledge-governor` | 平台知识治理员 | 平台知识主源、标准包和发布治理 |
| `organization-admin` | 机构管理员 | 集团、医院、分院或基层机构管理；层级差异由组织范围决定 |
| `identity-access-admin` | 人员与访问管理员 | 人员、任职、账号、身份来源和授权维护 |
| `knowledge-governor` | 机构知识治理员 | 机构知识派生、审核、发布和恢复平台标准 |
| `clinical-governor` | 临床治理负责人 | 规则、路径、临床运行和高风险审核 |
| `clinical-decision-user` | 临床决策使用者 | 医师等需要处理临床提醒、路径和人工确认的人员 |
| `nursing-collaborator` | 护理协同人员 | 护理任务、路径协同、随访和通知 |
| `medication-safety-user` | 药事安全人员 | 用药规则、药学知识和用药风险复核 |
| `diagnostic-service-user` | 医技协同人员 | 检验、影像、病理等结果接入和术语映射 |
| `quality-governor` | 质量与医保治理员 | 质控、病案、医保审核、整改和评价 |
| `compliance-auditor` | 合规审计员 | 独立审计、证据和受控导出 |
| `integration-operator` | 集成运维员 | 统一身份、适配器、运行状态和国产化运维 |
| `implementation-operator` | 实施运维员 | 客户开通、初始化、批量导入和联调验收 |

`system-superadmin` 仅是首次部署与紧急接管使用的系统内置角色，不属于客户可分配角色。

集团管理员和医院管理员不再是两个角色；二者都是 `organization-admin`，分别绑定集团或医疗服务机构节点。科主任、医师、护士、药师、医技技师、医务处、质控办、医保办和信息科均作为任职岗位或部门存在，再按实际责任组合职责角色。运行时拒绝所有早期角色编码，不提供转换、映射或兼容读取。

#### 账号 `tenant_user` + `platform_credential`

账号是登录入口和安全状态投影：

- `tenant_user` 继续作为权限和审计引用的稳定用户主体；
- `platform_credential` 仅保存平台托管凭证；
- 人员与账号通过 `person_account_link` 显式关联；
- 外部统一身份用户可以没有平台凭证。

#### 身份来源 `identity_binding`

外部身份绑定到人员，而不是让管理员从技术用户 ID 猜测自然人。认证成功后由人员的有效账号和任职求值权限。外部身份原文不落库，只保存国密摘要和脱敏提示。

### 2.3 医疗知识血缘

知识资产分为三种来源：

- 平台标准：直接读取平台当前已发布权威版本。
- 本地定制：从某个平台版本派生，保留平台身份和基线版本血缘，同一业务键在指定组织范围优先生效。
- 本地新增：客户独立创建，没有平台上游，不得反向成为平台或其它客户的上游。

定制生命周期：

1. 机构知识管理员选择平台标准和适用组织。
2. 系统创建本地草稿，保存不可变基线引用。
3. 本地编辑、证据补充、审核、试运行和发布沿用现有医疗安全门禁。
4. 发布成功后原子注册组织范围覆盖。
5. 平台后续更新不自动覆盖本地定制，页面显示“平台有新版本”，支持差异审阅和人工换基线。
6. “恢复平台标准”只停用本地覆盖，不删除本地版本和审计血缘。

## 3. 批量入职与绑定

导入模板的稳定业务字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `employeeNo` | 是 | 租户内人员工号或合作人员编号，用于幂等匹配 |
| `displayName` | 是 | 姓名 |
| `organizationCode` | 是 | 组织编码，由系统解析为组织树节点 |
| `departmentCode` | 否 | 科室编码 |
| `appointmentType` | 是 | 院内员工、集团共享、外部协作、实施运维 |
| `positionTitle` | 否 | 岗位或职称 |
| `loginName` | 否 | 需要平台账号时填写 |
| `roleCode` | 否 | 初始业务角色 |
| `identityProvider` | 否 | 员工号、统一身份、国密证书等 |
| `externalSubject` | 否 | 外部身份标识，仅在提交阶段进入摘要计算 |

匹配顺序：

1. 员工号精确匹配人员。
2. 登录名精确匹配账号。
3. 外部身份摘要精确匹配绑定。
4. 姓名只作冲突提示，绝不自动合并。

任务状态：

- 待校验
- 存在问题
- 可提交
- 处理中
- 部分成功
- 已完成
- 已取消

每行结果必须明确为新增、更新、跳过、冲突或失败。重复提交同一导入任务保持幂等。

## 4. 页面信息架构

### 4.1 登录

默认只展示机构选择、账号和密码一个主动作。平台治理入口折叠为受限入口，不向医院用户展示 `t-1`。统一身份入口只在真实接入时可用，未接入时诚实显示状态。

### 4.2 人员与账号

首页目标是回答“有哪些人、在哪里任职、是否能登录、权限是否合适”。

默认列：

- 姓名/工号
- 主任职机构和科室
- 人员类别
- 账号与身份来源
- 角色摘要
- 状态

主按钮为“批量导入”，单个新增放入次级操作。详情按“基本信息、任职、账号与认证、角色权限、变更记录”分区。

### 4.3 身份来源

首页按人员展示绑定状态，不再要求管理员先理解系统用户 ID。支持批量匹配未绑定人员、导入外部身份清单和冲突处置。

### 4.4 知识治理

列表直接显示：

- 来源：平台标准、本地定制、本地新增
- 当前生效范围
- 权威版本状态
- 平台更新状态

平台标准的主操作是“定制为本机构版本”；本地定制的主操作是“继续维护”；恢复平台标准是高影响次级操作，必须说明影响范围并保留审计。

## 5. 中文化标准

1. 枚举编码只用于接口、日志和专家模式。
2. 表格、标签、筛选项、弹窗、空态、错误态统一经过中文词典。
3. 身份协议可保留行业缩写，但必须带中文解释，例如“统一身份（OIDC）”。
4. `TENANT` 显示为“客户机构”，`REGION` 显示为“集团/医联体”，`FACILITY` 显示为“医疗服务机构”。
5. `ASSET`、`MEDIUM` 等不得直接显示，分别显示“资产维度”“中风险”等业务表达。
6. 未知枚举不得静默回显英文，统一显示“未知状态（编码）”并进入前端监测。

## 6. 安全与审计

1. 人员敏感标识不明文进入日志；外部身份只落摘要和脱敏提示。
2. 批量导入文件设短期保留，提交后只保留摘要、行级结果和审计证据。
3. 高权限角色批量授予必须二次确认，系统超级管理员不得通过客户批量导入创建。
4. 停用人员默认停用账号和有效身份来源，但不删除历史任职、角色和审计记录。
5. 知识定制、发布、换基线、恢复平台标准均进入统一审计链。

## 7. 全职责验收矩阵

| 角色 | 必须顺畅完成的任务 | 阻断标准 |
|---|---|---|
| 平台治理管理员 | 治理唯一平台空间、客户空间和全局授权 | 出现第二平台主源或可跨客户污染 |
| 平台知识治理员 | 发布平台标准、查看派生使用、升级提示 | 来源和版本血缘不清 |
| 机构管理员 | 按授权组织管理集团、医院、分院或基层机构 | 角色名绑定机构层级或需要手填范围编码 |
| 人员与访问管理员 | 导入人员、建立任职、开通账号、批量绑定身份 | 人员与账号混淆、冲突不可处理 |
| 临床治理负责人 | 在授权机构或科室内治理规则、路径和高风险审核 | 数据范围泄漏或作者自审 |
| 临床与护理协同人员 | 使用平台知识或本地定制，处理本人职责内任务 | 无法识别知识来源或误认为自动诊疗 |
| 外部协作人员 | 仅在有效任职和授权范围内访问 | 离职/到期后仍可访问 |
| 合规审计员 | 追溯人员、任职、账号、身份和知识全部变更 | 缺少操作者、时间、原因或前后值 |
| 集成运维员 | 配置统一身份、批量匹配、查看真实接入状态 | 未接入却显示可用 |
| 机构知识管理员 | 从平台标准派生、审核、发布、恢复平台标准 | 定制污染平台或失去基线 |
| 实施运维人员 | 使用模板导入、定位失败行、幂等重试 | 重试重复建人或返回假成功 |

验收要求：所有角色的主任务均可在前台完成；六态齐全；无客户可见裸英文枚举；自动化测试、五方言迁移、T-GATE、构建和浏览器实测全部通过；关键角色无 P0/P1 缺陷。

## 8. 实施边界

本次直接完成权威模型和关键前台闭环，不为错误的自由文本范围、技术用户选择器、逐条导入流程或早期角色编码保留兼容入口。134 环境清库后按当前迁移从零初始化，不执行旧角色数据转换。

## 9. 演练前全系统产品门禁

本重构提交后，先执行[全系统功能与产品信息架构重构设计](2026-06-11-global-product-ia-refactor-design.md)：盘点全部现有能力，按客户任务裁决保留、重命名、移位、合并、拆分、专家化、接口化或移除；同步重构功能名称、需求内容、菜单分类顺序、角色工作台和页面六态。该门禁经全角色桌面与移动端评审通过后，才允许进入 134 清库演练和第二阶段。
