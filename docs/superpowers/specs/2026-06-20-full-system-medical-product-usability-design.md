# 全系统医疗产品体验梳理与模型生产控制台设计

## 目标

把 MedKernel 从“功能已经很多，但用户不知道从哪里开始、下一步去哪里、不同角色如何接力”的工程系统，收敛成一套可由医院和知识生产中心真实使用的医疗产品。

本设计同时解决两类问题：

1. 全系统功能顺序、归类、角色入口、页面目标、状态和异常恢复缺少一致产品逻辑；
2. 模型生产相关的 Provider、模型 Key、医学评测、专家签署、九项 readiness 和知识生产任务分散，导致真实用户必须依赖脚本、数据库和多个页面。

完成后，任何功能必须能回答四个问题：

- 谁在什么场景使用；
- 从哪里进入；
- 当前状态是什么、下一步是什么；
- 完成后由谁接力、证据在哪里。

## 当前事实与根因

### 已确认的系统规模

- 前端约 50 个页面组件、37 个页面已直接使用统一 PageShell；
- 后端 93 个 Controller、约 597 个 HTTP 映射；
- H2 迁移已到 V157，五方言必须继续一致；
- 14 个客户职责角色已有权限快照和工作台旅程；
- 现有自动化能证明页面可打开，但不能充分证明用户能完成任务。

### 已确认的结构性问题

1. **目录完整不等于任务可完成**：现有路由烟测主要验证标题、权限、HTTP 错误和横向溢出，没有覆盖每个页面的主任务闭环。
2. **模型生产链入口割裂**：
   - Provider 配置和启停只有后端 API；
   - `/system/providers` 是运行依赖状态页，不是模型 Provider 管理；
   - 医学评测在 `/qc/model-evaluations`；
   - readiness 在知识生产页和验收自检页重复展示；
   - 版本与策略在 `/advanced/ai-workflows`；
   - 生产任务在 `/knowledge/production`。
3. **修复入口指向错误**：验收自检中的 `MODEL_PROVIDER` 指向运行保障，`MODEL_EVALUATION` 指向模型能力，而不是实际可完成操作的入口。
4. **工作台旅程存在遗漏**：质量治理员虽然拥有医学回归复核菜单，但其高频任务没有该入口；模型生产相关角色也缺少统一“当前做到哪一步”的任务视图。
5. **生产语义冲突**：正式知识生产入口允许用户选择非模型生产者，和“当前正式知识全部由大模型生产”的运营要求不一致。
6. **Key 维护缺口**：当前凭据只能在服务器环境变量维护。该方式安全但不具备前台轮换、状态查看和审计闭环。
7. **历史 B0 候选干扰审核池**：当前未激活的非模型候选和待审任务会继续出现在知识治理流程中，容易被误当成正式模型知识。
8. **产品面混杂**：知识生产中心的技术治理对象和医院临床运行任务共用角色、菜单与术语，用户容易进入不属于自己的工作面。

## 方案比较

### 方案 A：逐页修补现有入口

保留所有页面和菜单，只补链接、空态和说明。

优点是改动小；缺点是继续维持分散操作，用户仍需理解 Provider、评测、P6、版本三元组等技术关系，不能解决根因。

### 方案 B：只重排菜单

调整功能顺序和分类，但不改变页面边界与工作流。

优点是视觉上更整齐；缺点是页面之间仍没有状态接力，菜单会变成“整理过的功能仓库”，而不是任务产品。

### 方案 C：任务导向重构 + 统一模型生产控制台（采用）

以工作台、业务域、页内步骤和专家模式四层组织产品；用统一控制台承载模型生产完整状态机；对全系统逐角色执行真实任务验收，并按 P0/P1/P2 连续修复。

该方案改动范围更大，但能同时解决功能归类、角色协作、安全边界和真实可用性问题。

## 产品体验原则

### 一页一目标

每个客户页面只有一个主目标和最多一个主按钮。次级能力进入页签、抽屉或详情，不再堆叠同权操作。

### 任务先于技术对象

默认视图使用医院和治理语言：

- “配置模型服务”而不是“编辑 Provider Record”；
- “医学证据复核”而不是“Eval Run”；
- “生产前检查”而不是“Readiness API”；
- “开始生产知识”而不是“Create API_MODEL Job”。

providerCode、traceId、prompt/tool/model 三元组、凭据引用和原始 JSON 只在专家模式展示。

### 医疗安全前置

- AI 内容必须显著标识；
- 模型只生成候选，不直接成为权威事实；
- 医学复核人与生产执行人分离；
- 高风险内容继续双签；
- 缺少任一门禁时主动作禁用并显示明确修复入口；
- 不因“推进工程”绕过 MFA、职责分离、当前制品指纹或来源证据。

### 诚实状态和可恢复性

每页具备加载、空、错误、无权限、部分成功和正常六态。错误态必须显示中文原因、重试入口和 traceId；空态必须说明“为什么为空”和“下一步去哪里”。

## 全系统信息架构

### 1. 工作台

只回答：

- 当前职责；
- 最重要的一件事；
- 我的待办；
- 当前阻断；
- 最近证据。

工作台不再展示无法行动的指标。所有卡片必须能下钻到真实对象。

### 2. 机构与人员

顺序固定为：

1. 服务机构；
2. 人员与账号；
3. 身份来源。

开通机构后再建人、再绑定身份，符合实施顺序。

### 3. 知识治理

顺序按知识生命周期组织：

1. 来源与血缘；
2. 术语与字典；
3. 机构知识；
4. 诊断知识维护；
5. 规则配置；
6. 路径配置；
7. 配置包与发布；
8. 知识审核与发布；
9. 知识关系。

“来源 → 结构化维护 → 组包 → 审核发布 → 关系查看”优先于按技术模块罗列。

### 4. 知识生产

知识生产侧独立于医院临床运行侧，顺序为：

1. 模型生产控制台；
2. 生产任务与候选；
3. 智能工作流。

第一批先用一个“模型生产控制台”统一 Provider、Key、评测、签署、九闸和启动生产；现有生产 job、候选、门禁、影子和分流详情作为同页后半段或任务详情。

### 5. 临床协同

顺序按患者工作流组织：

1. 患者索引；
2. 患者路径；
3. 提醒与推荐；
4. 协同任务；
5. 随访协同。

全真体验沙盘不作为临床日常入口，移动到系统运维的实施验收工具或仅对实施/治理角色显示。

### 6. 质量管理

顺序按“发现 → 处置 → 规则”组织：

1. 质量管理概览；
2. 质量问题与整改；
3. 医保审核；
4. 评价指标。

医学回归复核从医院质量日常任务中移出，归入知识生产控制台；质量治理专家在平台生产空间内完成该步骤。

### 7. 合规安全

顺序固定为：

1. 审计与证据；
2. 安全与配置。

安全配置页继续承载系统配置、数据权限、脱敏和互操作测评；模型 Key 不在该页维护，避免普通系统配置和高敏模型凭据混用。

### 8. 系统运维

顺序按实施和故障处理组织：

1. 实施与验收；
2. 系统接入；
3. 运行保障；
4. 国产化核验；
5. 诊断工具。

运行保障只展示服务、依赖、备份恢复与真实健康，不再承担模型 Provider 配置。

## 模型生产控制台

### 页面目标

让生产中心用户在一个页面完成“配置 → 验证 → 评测 → 复核 → 放行 → 生产”，无需数据库、服务器环境文件或脚本。

### 页面步骤

#### 步骤 1：模型服务与 Key

- Provider 列表；
- 类型、服务地址、模型版本；
- Key 状态：未配置 / 已配置 / 待轮换；
- Key 指纹尾标、更新时间、更新人；
- 保存配置后强制保持停用；
- 真实健康检查；
- 高危启用和停用。

Key 输入为密码框，禁止自动填充；保存成功后立即清空，后端永不回显明文。

#### 步骤 2：医学评测

- 选择能力；
- 运行当前制品、当前基准、当前 Provider 和模型版本的真实评测；
- 展示逐例证据完整性、来源引用、红线和幻觉结论；
- 历史制品评测明确标识为“仅审计，不可放行”。

#### 步骤 3：独立复核

- 只有 `llm.eval.manage` 且满足 MFA、职责分离的用户可签署；
- 复核人必须逐例查看证据、确认声明并填写实质意见；
- 运行人不能签署自己的评测；
- 页面清楚显示当前步骤应由哪个角色完成。

#### 步骤 4：九项生产闸

按依赖顺序展示：

1. 文献资料库；
2. 部署形态；
3. Provider；
4. 医学回归基准；
5. 医学评测；
6. 出域治理；
7. 模型策略；
8. 版本三元组；
9. P6 独立验收。

每项提供状态、原因、证据摘要和正确修复入口。当前用户无权修复时显示责任角色，不显示不可用按钮。

#### 步骤 5：生产任务

- 正式前台只允许 `producer=API_MODEL`；
- 用户选择来源范围、资产类型、能力和 Provider；
- 系统显示将使用的模型版本和来源范围；
- readiness 未全绿时不能提交；
- 成功后进入 job 进度、候选、11 门禁、8 态分流和影子证据；
- 模型失败时诚实失败，不自动把任务改成 B0 候选。

### 角色协作

| 职责 | 可操作内容 |
|---|---|
| 集成运维员 | Provider、Key、健康检查、受控启停 |
| 质量治理专家 | 运行评测、逐例复核与签署 |
| 平台知识治理员 | 选择来源和资产类型、创建生产任务、处理候选 |
| 系统超级管理员 | P6 独立验收与高危放行 |
| 其他角色 | 仅查看与自身职责相关的状态，或不可见 |

同页不等于同权。前端按权限显示操作，后端仍逐接口强制权限、租户、MFA、职责分离和乐观锁。

## 模型 Key 安全设计

### 存储

新增 `mk_llm_provider_credential`：

- `tenant_id`；
- `provider_code`；
- `credential_ciphertext`；
- `credential_fingerprint`；
- `credential_last4`；
- `lock_version`；
- 创建/更新人、时间和 traceId。

密文使用现有 `MEDKERNEL_FIELD_ENCRYPTION_KEY` 派生独立用途密钥，以 SM4 加密；Provider Key 和 D3/D4 字段使用不同派生上下文，不能互相解密。

数据库、API、审计和日志均不得出现明文。审计只记录 Provider、操作类型、指纹尾标、版本和 traceId。

### 兼容

凭据解析顺序：

1. 当前租户加密凭据库；
2. 既有环境变量引用。

这样可以安全迁移现有 134 配置，不要求一次性停机换 Key。前台保存新 Key 后，Provider 配置自动保持停用、健康状态重置，必须重新探活、评测和启用。

### API

- `GET /api/v1/model-providers`：分页列表；
- `PUT /api/v1/model-providers/{providerCode}`：保存脱敏配置；
- `PUT /api/v1/model-providers/{providerCode}/credential`：写入或轮换 Key；
- `DELETE /api/v1/model-providers/{providerCode}/credential`：移除 Key并强制停用；
- `POST /health-check`、`/enable`、`/disable`：沿用现有高危治理。

凭据写入和删除要求 `llm.provider.manage`、MFA、高危确认、原因和 expectedVersion。

## 仅大模型正式生产约束

### 产品边界

- 正式生产控制台只创建 `API_MODEL` job；
- 不向用户提供 AGENT_TOOL、LOCAL_MODEL、MANUAL 或 B0 生产者选择；
- 模型调用不成功时不产生候选；
- B0 确定性能力继续作为系统安全降级、测试和人工维护底座，但不能通过正式模型生产入口混入当前生产批次。

### 后端边界

公共正式生产接口拒绝非 `API_MODEL`；
内部初始化、迁移和 B0 回归继续走明确的内部服务边界，不使用正式控制台接口。

### 历史候选清理

不物理删除审计事实。对当前所有满足以下条件的候选执行受控撤回：

- `generatedByModel=false` 或生产 job `producer != API_MODEL`；
- 尚未激活；
- 当前状态为待编著、待审核或待替换审核；
- 属于本次清理确认的基础 B0 批次和 WHO B0 样本。

处理结果：

- 候选版本进入 `WITHDRAWN` 或等价终态；
- 分类和审核任务进入 `REJECTED`/关闭态；
- job 保留原状态和生产证据，增加“非模型候选退出正式生产池”的审计原因；
- ACTIVE 知识不受影响。

## 全系统梳理方法

### 功能清单

以 `routes.ts`、`MenuPermissionCatalog`、Controller、迁移、施工卡和角色旅程共同建立唯一清单。每项记录：

- 产品面和业务域；
- 主角色和协作角色；
- 菜单/页内/API-only 承载；
- 前端页面和后端接口；
- 主任务；
- 六态；
- 数据量和分页；
- 审计证据；
- 当前结论和问题等级。

### 真实旅程

对 14 个职责角色逐一执行：

1. 登录和工作台；
2. 唯一主动作；
3. 高频任务；
4. 跨角色接力；
5. 错误和无权限；
6. 审计与证据。

页面可打开不算通过，必须完成一条真实任务或得到诚实、可行动的空态。

### 问题分级

- **P0**：无法完成关键任务、医疗安全风险、权限或凭据泄漏、错误入口导致错误操作；
- **P1**：任务需要脚本/数据库、多页面反复跳转、角色接力断裂、状态或修复入口错误；
- **P2**：命名、排序、信息密度、可访问性、移动端或效率问题。

### 修复顺序

1. P0 安全和任务阻断；
2. P1 信息架构和跨页闭环；
3. P2 体验、效率和一致性；
4. 每批完成后重新跑受影响角色旅程和全量路由烟测。

## 测试与验收

### 自动化

- 后端单测、契约、安全、五方言迁移；
- 前端 hooks、页面、路由、菜单和角色旅程；
- Playwright 14 角色主任务、全部授权路由、模型生产端到端；
- Key 明文泄漏扫描；
- 10 万级服务端分页；
- T-GATE、中文注释、产品目录和 `git diff --check`。

### 浏览器验收

每个 P0/P1 修复至少提供：

- 角色；
- 页面路由；
- 操作步骤；
- 结果；
- 错误/空态；
- 桌面和 390px 窄屏；
- 控制台和 HTTP 错误为零。

### 发布

每批独立 PR、CI 全绿、合并 `main` 后部署 134。部署后重新核对运行指纹、Flyway、健康、角色页面和关键数据状态。

模型生产控制台上线前不得继续生成新的 B0 候选；清理历史非模型候选后，只有真实模型任务可以进入正式审核池。

## 完成判据

只有同时满足以下条件，才能声明“系统可正常使用”：

- 所有认证路由有明确归类和主角色；
- 14 角色主任务可从工作台完成起步；
- P0 为零，P1 全部关闭或有不影响当前使用的明确外部依赖；
- 模型生产完整链路可在一个控制台完成；
- 模型 Key 可在前台安全录入和轮换且永不回显；
- 正式生产入口只能创建大模型任务；
- 非模型未激活候选已退出正式审核池；
- 六态、服务端分页、医疗安全、职责分离和审计证据通过；
- 前后端全量门禁、真实浏览器旅程和 134 部署复核通过；
- `_HANDOFF.md`、角色旅程、功能目录和实际系统一致。
