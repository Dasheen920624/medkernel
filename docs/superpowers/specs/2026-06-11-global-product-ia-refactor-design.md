# 全系统功能与产品信息架构重构设计

## 1. 定位与执行时点

本重构是第一阶段代码完成并提交后、193.112.107.134 清库演练前的强制产品门禁。它不只检查现有页面是否可打开，而是重新判断每项能力是否应当存在、叫什么、归属哪里、由谁使用、如何完成任务，以及是否值得作为客户可见功能保留。

未通过本门禁，不得进入 134 演练；未完成 134 双重演，不得进入第二阶段。

用户已授权按最优方案自主裁决，不为旧菜单、旧名称、旧页面拆分或历史文档保留兼容。

## 2. 重构目标

1. 形成唯一、完整、可追溯的功能目录，覆盖前端页面、后端能力、批量任务、第三方接口和专家工具。
2. 消除同义名称、技术名称、重复入口、功能归属错误和实施期临时概念。
3. 让 14 个客户职责角色登录后只看到与当前任务有关的入口，并有清晰的默认工作台。
4. 把“试点时怎么配置”和“正式运行时怎么使用”统一成长期可维护的产品结构。
5. 确保客户可见页面使用医疗服务机构语言，不暴露英文枚举、技术编码、内部引擎名、JSON、DSL 或原始 trace。
6. 使每个保留功能都具备明确主任务、完整六态、真实数据来源、权限边界、审计证据和可验收路径。

## 3. 功能裁决模型

每项现有功能必须进入以下一种结论，不允许以“先留着”结束：

| 裁决 | 适用条件 | 处理 |
|---|---|---|
| 保留 | 客户任务明确、归属正确、无重复 | 优化名称、文案、默认视图和状态 |
| 重命名 | 能力正确但名称技术化、模糊或角色不理解 | 同步菜单、页头、面包屑、权限目录、手册和测试 |
| 移位 | 功能有价值但当前一级/二级归属错误 | 移入目标业务域并更新角色入口 |
| 合并 | 多页完成同一任务或客户需跨页拼接 | 合为一个任务页，原能力成为页内步骤、标签或抽屉 |
| 拆分 | 单页承担互不相干的多个目标 | 按任务拆分，但不机械增加菜单；优先页内子视图 |
| 专业化 | 只对实施、集成、审计或平台治理有意义 | 根据任务连续性、风险和使用频率，裁决为同页渐进披露、专业工作区或独立入口 |
| 接口化 | 只服务 HIS/LIS/EMR/第三方系统 | 从客户菜单移除，进入第三方对接案例和接口文档 |
| 移除 | 无真实业务目标、重复、演示占位或错误设计 | 删除代码、路由、权限、文档和测试，不保留兼容入口 |

## 4. 信息架构裁决原则

本设计不预设一级菜单数量、固定分组、固定顺序，也不预设专业能力必须隐藏或必须独立成组。现行 `5+1`、五个客户主域、单列高级工具等结构均作为待验证方案进入裁决，不作为实施前提。

最终架构必须从医疗引擎中枢的产品使命和真实任务网络推导，至少比较：

- 按医疗业务领域组织；
- 按角色任务与工作阶段组织；
- 按治理、配置、运行、监测和交付生命周期组织；
- 领域导航与角色工作台结合的混合结构；
- 专业能力在同页渐进披露、专业工作区或独立入口之间的不同承载方式。

裁决证据包括任务频率、角色重叠度、跨页切换成本、风险等级、上下文连续性、移动端适配、权限复杂度、实施交付成本和客户可发现性。不得为了满足既有菜单锁而强行合并无关任务，也不得为了展示能力而机械增加入口。

候选能力域至少覆盖但不限于：

- 当前任务与风险处置；
- 服务机构、组织、人员、账号和身份来源；
- 平台知识主源、机构派生、规则、路径、字典和发布；
- 临床运行、患者路径、提醒推荐、任务通知和随访；
- 质量、医保、评价、整改和运营；
- 安全、审计、运行保障、集成和交付；
- 来源追溯、知识关系、智能工作流、国产化核验和开发诊断等专业能力。

这些是能力盘点维度，不等同于最终菜单。盘点完成后，须同步修订 `CONSTITUTION`、体验契约、菜单目录、路由、权限矩阵和客户手册，使新裁决成为唯一权威。

## 5. 命名标准

1. 菜单使用稳定业务对象或任务名称，不使用项目阶段、技术组件或实现名。
2. 页面标题回答“这里管理什么”，按钮回答“现在做什么”。
3. `tenant` 统一为“服务机构”或“机构空间”，不在客户面显示“租户”。
4. `Provider` 统一为“外部依赖”或具体系统名称。
5. “用户管理”统一为“人员与账号”，“身份绑定”统一为“身份来源”。
6. “临床提醒治理”统一评估为“提醒与推荐”；只有治理角色视图才使用“治理”。
7. “客户实施向导”在客户长期使用场景下统一评估为“实施与开通”。
8. 行业缩写仅保留 ICD、DRG、DIP、MPI、FHIR、OIDC 等必要术语，并提供中文解释。

## 6. 页面级产品契约

每个保留页面必须登记：

- 主角色和协作角色
- 单一主目标
- 入口与上一步
- 一个主动作
- 不超过三个默认筛选
- 默认八列以内的客户字段
- 加载、空、错误、无权限、部分成功、正常六态
- 真实 API 和数据权威
- 组织范围、动作权限、资产权限和环境限制
- 医疗安全风险及人工确认点
- 审计和证据入口
- 桌面、1366×768、平板和 390px 移动视口行为

后端有能力但无客户入口的，必须明确并入哪个页面或登记为接口能力；不允许继续宣称为客户功能。

## 7. 全角色任务旅程

14 个客户职责角色分别建立“登录 → 默认工作台 → 高频任务 → 异常处置 → 审计/证据”旅程。一个角色不要求理解与其职责无关的系统术语；一个关键任务不得依赖多个菜单间猜测跳转。

重点评审：

- 平台治理管理员：平台空间、机构空间、授权和运行治理。
- 平台知识治理员：平台主源、标准包、发布和派生影响。
- 机构管理员：服务机构、组织和机构级策略。
- 人员与访问管理员：批量导入、任职、账号、身份来源和授权。
- 机构知识治理员：机构派生、差异、审核、发布和恢复平台标准。
- 临床治理负责人：规则、路径、高风险审核和临床运行治理。
- 临床、护理、药事、医技：在职责范围内完成任务，不承担平台配置。
- 质量与医保治理员：问题发现、整改、评价和医保审核。
- 合规审计员：独立只读证据链和受控导出。
- 集成运维员：系统接入、运行状态和失败补偿。
- 实施运维员：开通、导入、初始化、联调和验收。

## 8. 验收门禁

必须同时通过：

1. 功能目录中每项能力都有唯一裁决、唯一归属和唯一责任页面。
2. 后端菜单目录、前端路由、页面卡、角色权限和客户手册完全同源。
3. 不存在重复菜单、孤儿路由、无入口客户能力、假入口或权限可见但不可用。
4. 所有客户可见名称、枚举、状态、错误和操作为中文业务表达。
5. 14 角色菜单快照、默认工作台和主任务全部通过桌面与移动端验收。
6. 所有页面满足一页一目标、一个主按钮、三个默认筛选、六态和真实数据。
7. 医疗安全、最小权限、数据最小化、审计和诚实降级评审无 P0/P1。
8. 自动化信息架构门禁、前端全量测试、后端全量测试、T-GATE 和浏览器走查全部通过。
