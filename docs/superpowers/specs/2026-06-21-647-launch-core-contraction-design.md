# #647 完整上线重构设计

## 1. 设计边界

本设计只以 PR #647 合并提交 `acd511c0` 为原始代码基线，不读取、比较或继承 #648、#649 的方案。

本轮不是首发裁剪，也不是把 MedKernel 改成只有知识后台的最小系统。目标是：

1. 保留全部真实业务页面、接口和引擎能力；
2. 将医疗引擎、知识生产和 SaaS 平台管理重新分区；
3. 删除无法落实的专家委员会、双人签署、角色兼容和租户权限覆盖；
4. 把医疗安全从“必须凑齐多人”改为“技术门禁 + 单一责任确认 + 可回滚”；
5. MFA 默认关闭，显式开启后执行真实登录二次校验；
6. 迁移压缩为一份规范化模式模型和五份自动生成的 V1；
7. 清除过期方案、截图和演练证据，只保留当前上线真相；
8. 清库部署后完成大模型自动生成知识、审核、发布、运行和回滚演练。

项目尚未上线，不保留旧角色、旧迁移、旧接口或旧文档兼容。

## 2. 全量核查结论

### 2.1 真实能力规模

| 对象 | 数量 | 决策 |
|---|---:|---|
| 前端路由元数据 | 44 | 全部保留；根重定向不算业务功能 |
| 前端页面组件 | 54 | 不因本轮简化删除业务页面 |
| 后端 Controller 文件 | 93 | 保留真实接口能力 |
| `@RestController` 类 | 95 | 保留 |
| `@PreAuthorize` | 501 | 保留权限校验，改为单一权限模型 |
| 菜单目录项 | 34 | 32 个侧栏入口、通知页头、通知偏好个人入口全部保留 |
| 权限编码 | 115 | 作为内部授权原子保留 |
| 角色枚举 | 15 | 重建为 4 个可分配职责 + 1 个内置超管 |
| 五方言迁移 | 795 | 删除历史链，生成五份 V1 |
| 最终表 | 214 | 以终态模式模型为准 |

现有临床协同、质量医保、组织人员、系统接入等页面不是冗余。此前把它们隐藏、只保留五个中枢域的设计会丢失完整上线能力，予以废止。

### 2.2 当前四角色提交的反证

本地提交 `adc5a33d` 只允许分配四个旧角色，但其默认权限只覆盖 25 个菜单项，以下 9 个真实入口没有任何可分配角色：

- 患者索引；
- 患者路径；
- 提醒与推荐；
- 协同任务；
- 随访协同；
- 质量问题与整改；
- 医保审核；
- 评价指标；
- 消息通知。

因此不能继续采用“挑四个旧角色，其余兼容保留”的方案。角色必须按完整功能重新组合。

### 2.3 复杂度根因

当前权限实际存在三套并行判断：

1. `RoleCode -> DefaultPermissionPolicy`；
2. 租户级 `role_permission` ALLOW/DENY 覆盖；
3. 前端 `requiredPermissions + requiredRoles` 双重判断。

此外，部分服务继续直接判断具体角色，形成第四套隐性规则。角色、权限、菜单和服务职责互相重复，才是“看得到却做不了”的主要原因。

当前 MFA 也不是真正的登录 MFA：账号密码成功后已签发完整 JWT，系统只检查是否绑定 TOTP，没有在登录时验证动态码。

## 3. 产品结构：三空间、八业务域、全部页面

左侧 SideMenu 继续作为主菜单。在侧栏顶部增加产品空间切换，空间内继续使用现有业务域和页面，不删除功能。

### 3.1 医疗引擎

面向引擎运营和临床运行：

- 工作台；
- 知识治理；
- 临床协同；
- 质量管理。

包含知识、术语、规则、路径、配置包、患者索引、患者路径、提醒推荐、待办、随访、沙盘、质控、医保和评价指标。

### 3.2 知识生产

面向自动化知识生产：

- 模型 Provider 与凭据；
- 医学回归和红线测试；
- 来源获取与解析；
- 大模型自动生成；
- 安全门、去重、影子验证；
- 候选审核、发布和回滚；
- 模型能力与降级状态。

知识生产不是可选演示功能，而是完整上线能力。无模型时医疗引擎仍可 B0 运行；选择模型生产任务时必须满足真实模型门禁。

### 3.3 平台管理

面向 SaaS 与部署运维：

- 机构与人员；
- 合规安全；
- 系统运维。

包含服务机构、组织、人员账号、身份来源、审计证据、安全配置、实施验收、系统接入、运行保障、国产化和诊断工具。

### 3.4 路由规则

- 44 条路由全部进入能力目录；
- `hidden` 只用于同一任务内的子页面，不再用于掩盖完整功能；
- `embedded` 继续用于嵌入终端；
- 路由只校验权限，不再重复校验角色；
- 每个菜单必须至少被一个可分配职责覆盖；
- 每个职责默认只进入与其任务相关的产品空间。

## 4. 最简权限模型

### 4.1 职责

| 编码 | 名称 | 责任 |
|---|---|---|
| `system-superadmin` | 内置超级管理员 | 系统应急与全量维护，不可手工分配 |
| `platform-admin` | 平台管理员 | SaaS、账号、身份、接入、配置、部署和运行 |
| `engine-operator` | 医疗引擎运营员 | 知识、规则、路径、质量、模型生产和发布 |
| `clinical-user` | 临床使用者 | 患者、路径、提醒、待办、随访、通知和临床确认 |
| `auditor` | 审计员 | 审计、来源、证据和运行事实只读核查 |

不再保留机构管理员、知识专家、临床专家、药事、医技、质量、实施、集成等兼容角色。专业身份由人员任职信息表达，不参与系统授权。

### 4.2 单一授权链

授权只保留：

```text
职责包固定权限 + 用户授权组织范围 + 当前请求组织范围
```

删除：

- `role_permission` 表；
- 租户角色权限覆盖仓库和接口；
- 菜单权限覆盖写接口；
- 前端 `requiredRoles`；
- 服务层对旧角色编码的直接判断；
- 兼容角色别名和历史 JWT 识别。

保留：

- `PermissionCode` 原子权限；
- `UserRoleAssignment`；
- 租户、集团、医院、院区、科室、病区、专病数据范围；
- 拒绝优先和租户隔离；
- 应急权限的显式、限时、审计授权。

组织范围是数据边界，不再伪装成角色。

### 4.3 菜单覆盖

- 平台管理员覆盖平台管理全部页面；
- 医疗引擎运营员覆盖知识治理、知识生产、质量管理和必要沙盘；
- 临床使用者覆盖临床协同和个人通知；
- 审计员覆盖审计、来源、证据和必要运行只读；
- 内置超管覆盖全部。

后端契约测试必须证明 34 个菜单零遗漏、零孤儿、零仅兼容角色入口。

## 5. 人员门阀清理与医疗安全保留

本轮删除的是无法落实的组织流程，不删除安全事实。

### 5.1 统一单一责任确认

以下流程取消“另一人、另一角色、委员会、专家、来源登记人与批准人必须不同”等要求：

- 高风险知识双签；
- 规则同行评审与委员会会签；
- 模型评测独立专家签字；
- 来源登记/停用独立审批；
- 来源版本登记人与批准人分离；
- 版本发布人与签字人分离；
- 导出申请人与审批人分离；
- 路径、配置包、评价指标的指定协调角色。

高风险动作改为：

```text
权限校验
→ 技术门禁通过
→ 展示影响与风险
→ 当前责任人逐条确认并填写原因
→ 原子执行
→ 审计、证据、回滚
```

同一责任人可以创建、确认和发布，但每一步必须有不可变审计事实。

### 5.2 必须保留的安全门

- AI 内容明显标识；
- 医师确认后才进入病历；
- 禁止自动开医嘱、签署、支付、上报和设备控制；
- 来源、版本、引用位置和摘要可追溯；
- 假引用、幻觉和红线用例任一失败即阻断；
- 新旧知识唯一权威与原子切换；
- 影子、灰度、全量、监测和回滚；
- 高危近似映射禁批量、逐条确认；
- 患者数据外调白名单、脱敏和部署形态限制；
- 关系数据库继续作为唯一业务事实权威源；
- 无模型、断连和依赖缺失必须诚实降级。

## 6. 规则、知识和模型状态

### 6.1 规则治理

删除 `PEER_REVIEW`、`COMMITTEE` 和签字人数，使用：

```text
DRAFT → REVIEWED → SHADOW → CANARY → FULL → MONITOR → RETIRED
```

- `REVIEWED` 是单一责任确认；
- `SHADOW/CANARY/FULL/MONITOR` 是技术和运行阶段，继续保留；
- 任一阶段可按真实失败回滚或退役。

### 6.2 知识候选

- 所有风险等级只生成一个审核责任；
- 删除 `requiresDualSign`、第二领域席位和 `PENDING_DUAL_SIGN`；
- HIGH 仍要求逐条确认、完整来源、影响分析和技术门禁；
- 批量批准只允许低风险且清单全部满足安全条件。

### 6.3 模型评测

- 每个启用基准必须实际运行；
- 所有用例通过、无假引用、无幻觉、无红线越界时直接 `PASSED`；
- 任一失败直接 `FAILED`；
- 删除 `PENDING_REVIEW`、独立专家签字接口和复核面板；
- 保留逐用例不可变证据、基准摘要和制品指纹，基准或制品变化必须重跑；
- 删除手工 P6 独立验收开关，readiness 只由可验证技术事实组成。

## 7. MFA：默认关闭，开启后真实生效

配置键：

```text
medkernel.auth.mfa.required=false
```

规则：

1. 默认 `false`，所有账号只使用账号密码；
2. 开启后对所有平台账号使用同一规则，不再按角色维护名单；
3. 已绑定账号必须在登录请求中提交 TOTP，验证成功后才签发完整会话；
4. 未绑定账号只签发受限引导会话，只允许改密、绑定 MFA、退出和读取当前安全状态；
5. 绑定完成后必须重新登录，完整 JWT 写入 `mfa_verified=true`；
6. 开启 MFA 后，高风险守卫校验当前会话已完成 MFA，而不是只看数据库是否存在 secret；
7. 关闭后不要求绑定，不阻塞登录或高风险动作；
8. TOTP secret 继续加密保存，恢复码只保存摘要。

## 8. 大模型自动生成知识完整链路

正式链路为：

```text
权威来源登记/获取
→ 原件 hash 与许可校验
→ 文档解析
→ Provider 健康与凭据
→ 当前制品医学回归
→ 出域/版本/策略 readiness
→ 大模型生成候选
→ 去重与新旧识别
→ 引用、结构、红线、安全门
→ 影子验证
→ 单一责任审核
→ 发布/激活
→ 运行读取
→ 反馈/撤回/回滚
```

清库演练必须生成一小批真实权威知识：

- 使用公开权威来源和可校验原件；
- 至少包含一条真实大模型生成候选；
- 候选标记 `generatedByModel=true`；
- 不伪造模型输出、引用、hash、RTT 或专家身份；
- 只选择能够由现有技术门和单一责任确认安全发布的低风险知识；
- 同时验证重复运行幂等、来源漂移阻断和旧版退出。

## 9. 数据库：一份模式模型，五份 V1

一份裸 SQL 无法可靠兼容 PostgreSQL、人大金仓、Oracle、达梦和 H2，原因包括类型、标识列、布尔值、时间戳、注释和条件建表语法不同。

采用：

```text
schema/medkernel.schema.json
        ↓ generator
postgres/V1__baseline.sql
kingbase/V1__baseline.sql
oracle/V1__baseline.sql
dm/V1__baseline.sql
h2/V1__baseline.sql
```

### 9.1 规范化模型内容

- 表、列、通用类型、长度、精度、可空、默认值；
- 主键、外键、唯一、检查约束；
- 索引；
- 中文表注释和列注释；
- 方言能力标记，仅允许集中在生成器适配层。

### 9.2 基线生成

1. 先用现有 V1–V159 在空 H2/PostgreSQL 得到终态；
2. 通过 JDBC 元数据和现有 PostgreSQL 中文注释提取规范化模型；
3. 人工核查删除历史列、旧角色、`role_permission`、双签和旧状态；
4. 生成五方言 V1；
5. 删除 V2–V159；
6. 应用级静态目录由代码播种器维护，迁移只负责结构；
7. 生成器必须幂等，生成后仓库无 diff；
8. 用模式指纹比较表、列、类型语义、约束、索引和注释。

### 9.3 验证

- H2 空库；
- PostgreSQL Testcontainers 空库；
- Oracle XE Testcontainers 空库；
- Kingbase/DM 静态生成契约；
- 134 实际目标方言空库部署；
- 五方言均只显示 V1。
