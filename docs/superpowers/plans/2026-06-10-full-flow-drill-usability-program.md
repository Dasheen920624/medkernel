# 全流程演练 · 使用指南 · 体验重构 总体计划

> **接力执行须知**：本计划是「第一版就绪 → 第二阶段（批量知识生产）」之间的总闸门工程，供多个 AI 会话接力执行。
> 开工先读 [docs/_HANDOFF.md](../../_HANDOFF.md) 拿当前幕次与状态，再读本计划对应幕节，**不要通读全文后再开工**。
> 执行规约遵守 [AGENTS.md](../../../AGENTS.md)（中文、分支→PR、文档随代码同 PR、token 经济）与 [CONSTITUTION](../../CONSTITUTION.md) 11 铁律。
> 缺陷修复一律 TDD；体验优化先提案后实现（见 §8 双轨工作流）。

**目标**：用 134 服务器做一次全功能、真实医疗数据的全流程演练，产出客户看得懂的全套使用指南，并以顶级医疗产品体验师视角完成全系统可用性重构——三者达标后才进入第二阶段。

**方法**：演练即审计——每走一幕，同步产出「证据 + 词条 + 指南章节 + 体验评审 + 缺陷/优化提案」五件套；演练数据全部为医学上正确的真实知识内容，演练完按已实证流程清库。

**技术底座**：134（193.112.107.134，govcloud + PG15，main `b2e7329e`，Flyway 113/113）；前端 React + antd + @xyflow/react（流程图能力已具备）；44 个页面（routes.ts 实测）、六大域信息架构；71 个后端 Controller（实测）；内置 14 角色（`RoleCode`，含系统超管）。

## §0 客户之声（为什么有本计划）

客户验收第一版后的原话级反馈，本计划的全部工作以消除这些痛点为准绳：

1. **「功能很多，但名词、用法全都看不懂，完全无法使用」** —— 语言与引导问题，不是功能缺失问题。
2. **「规则引擎、路径引擎配置后阅读很难理解」** —— 需要流程图/脑图等图形化阅读方式。
3. **「推荐引擎很迷糊，不懂在哪里」** —— 能力可见性问题：后端有 `RecommendationEngineController`，但前端 44 个页面中**没有任何「推荐」入口**（已勘察证实）。
4. **「其他不直观的功能也要提出优化」「全方位梳理重构优化」** —— 体验重构必须系统性覆盖全部页面，客户点名只是样本。

> 北极星判据：**一个没接触过本系统的医院信息科员工，拿着指南能独立走通主流程；一个医生 30 秒内能说出任一临床页面「是干什么的」。**

## §2 工作线与接力节奏

```
线A 演练验证（主线，幕0→幕10 顺序推进，幕内可并行）
线B 指南与词汇表（跟随线A：每幕收尾时写该幕对应章节+词条）
线C 体验重构（跟随线A：每幕做四问审计出提案；提案经用户确认后排期实现，
              已确认项可与后续幕并行开发）
```

- **一幕一节奏**：演练 → 证据 → 词条 → 指南草稿 → 体验评审 → 缺陷/提案 → 更新 `_HANDOFF.md` 演练线状态 → 一个 PR（文档+小修复可同 PR；大修复独立 PR）。
- 每个接力会话至少完成一幕或一个优化项，**不留半幕**；中断前必须把「下一步精确动作」写进 handoff。
- 134 操作授权：用户已授权从本机 SSH 全程执行（root@193.112.107.134，密钥 `~/.ssh/id_ed25519`）；改 nginx/systemd/env 类生产配置仍需用户点名授权（见 memory 教训）。

## §4 演练剧本（幕 0–10）

> 每幕结构：**目的 / 角色 / 入口 / 真实数据 / 关键动作 / 通过判据 / 同步产出**。
> 入口写前端路由；后端 Controller 名供排障定位。执行时以页面实际为准，页面与剧本不符即是「体验缺陷或剧本缺陷」，二者必居其一，登记后裁决。

### 幕0 · 部署接管与首次登录

- **目的**：验证从裸系统到可用的第一公里，这是客户实施工程师的第一体验。
- **角色**：信息科管理员（实施）。
- **入口**：`/bootstrap` 首次部署接管 → `/login`。Controller：`Bootstrap`、`Auth`、`SecurityMe`。
- **动作**：浏览器首访（自签证书告警是客户第一公里必撞点，记录处理方式，指南须含换证/信任指引）→ 读服务器接管码 → 创建平台管理员 → 首登改密 → 绑定 MFA（恢复码只展示一次）→ 进 `/workbench/readiness-validation` 验收自检看全系统就绪态。
- **通过判据**：接管完成；MFA 登录成功；验收自检页能看懂哪些项「就绪/阻塞/未启用」。
- **同步产出**：指南《合规运维手册》第 1 章「首次部署」；词条（接管码、MFA、恢复码、就绪态）；体验四问审计 `/bootstrap`、`/login`、验收自检页。

### 幕1 · 租户、组织与用户

- **目的**：建立「演练总医院」组织骨架与内置角色子集（`RoleCode` 共 14 个，含系统超管），验证五维权限。
- **角色**：平台管理员 → 租户管理员。
- **入口**：`/tenant/onboarding` 租户管理、用户管理页、`/onboarding/guide` 客户实施向导。Controller：`TenantProvisioning`、`TenantEngine`、`OrgUnit`、`MenuPermission`、`ComplianceUser`。
- **真实数据**：租户「演练总医院」；科室树：医务处、信息科、医保办、心内科、呼吸与危重症医学科、检验科、药学部；账号 9 个——信息科管理员（IT_OPS）、医务处质控员（MEDICAL_AFFAIRS）、医保办专员（INSURANCE_MANAGER）、心内科医生、呼吸科医生（DOCTOR）、呼吸科护士（NURSE）、检验技师、临床药师、审计员（AUDIT_COMPLIANCE）。
- **角色事实（已实锤）**：`RoleCode` 内置 14 角色**无「检验技师/临床药师」**，且 `UserRoleAssignment` 仅认枚举内角色——演练以专科专家（SPECIALIST）代配并验证其菜单边界，缺口登记 OPT-ROLE-01（§6.5）。本幕真实覆盖 ≥9/14 内置角色，未覆盖角色在交叉验证中各做一次登录可见性抽查。
- **动作**：开租户 → 建科室树 → 建账号配角色 → **交叉验证权限**（医生账号登录应看不到合规运维域；审计员只读）。
- **通过判据**：9 账号各自登录所见菜单与角色匹配；越权访问被拒并留审计；角色覆盖矩阵入证据目录。
- **同步产出**：《试点准备手册》第 1–2 章；词条（租户、组织范围、五维权限、角色）；实施向导页四问审计（这是客户第一次大规模配置的页面，重点评审）。

### 幕2 · 字典与术语对照

- **目的**：客户痛点重灾区——「字典注册、对照」全流程走通并讲明白。
- **角色**：信息科管理员、检验技师。
- **入口**：`/terminology/mapping` 字典映射。Controller：`Terminology`。
- **真实数据**：
  - 标准术语：ICD-10 `J15.9 细菌性肺炎`、`J18.9 肺炎`、`I21.0 急性前壁心肌梗死`；LOINC `2823-3 血清钾`、`718-7 血红蛋白`；ATC `B01AA03 华法林`、`B01AC06 阿司匹林`、`J01CR02 阿莫西林/克拉维酸`。
  - 本地术语（模拟院内 HIS/LIS 代码）：检验 `K001 血钾` → LOINC 2823-3；药品 `Y2035 华法林钠片2.5mg` → ATC B01AA03；诊断 `ZD0456 社区获得性肺炎` → ICD-10 J15.9。
- **动作**：登记标准术语 → 登记本地术语 → 建映射（草稿→已确认）→ 演示一次映射替换与回滚（状态机：草稿/已确认/已替换/已回滚）→ 制造一个映射冲突看系统怎么提示。
- **通过判据**：对照表可查可导出；状态机流转全留痕；冲突有可读提示。
- **同步产出**：《试点准备手册》「字典对照」章（含一张「院内代码→标准代码」示意图）；词条（标准术语、本地术语、映射、冲突）；提案预录 OPT-TERM-01（§6.4）。

### 幕3 · 知识治理（登记→会签→发布→追溯）

- **目的**：知识生产中心的核心主链，第二阶段批量生产的单件验证。
- **角色**：知识管理员（信息科兼）、医务处质控员（会签人）。
- **入口**：知识治理页、来源追溯页。Controller：`KnowledgeIdentity`、`KnowledgeVersion`、`Evidence`、`KnowledgeRetirement`。
- **真实数据**：知识源《中国成人社区获得性肺炎诊断和治疗指南（2016 年版）》＋《医疗机构临床实验室管理办法》危急值条款；从中登记 2 条知识资产：①CAP 经验性抗感染推荐；②血钾危急值阈值与报告时限。
- **动作**：登记知识源 → 拆条目 → 建知识资产与版本 → 双人会签 → 发布 → 在来源追溯页从资产反查到指南原文出处 → 演示一次版本升级与旧版退役。
- **通过判据**：未会签不可发布；发布后来源链完整；退役版本不再被引用。
- **同步产出**：《试点准备手册》「知识治理」章；词条（知识源、资产、会签、来源追溯、退役）。

### 幕4 · 规则引擎（危急值 + DDI + 医保）

- **目的**：三类代表性规则配置、测试、影子到生效全生命周期；**现场验证客户点名的「配置后读不懂」痛点**。
- **角色**：医务处质控员（R1 配置）、临床药师（R2 DDI 评审）、医保办专员（R3 医保规则配置，对位 `InsuranceQuality`）。
- **入口**：`/rule/definitions` 规则库、`/rule/validate` 规则校验。Controller：`RuleEngine`、`ClinicalRedline`、`CdssRiskMatrix`、`InsuranceQuality`。
- **真实数据**：
  - R1 危急值：血清钾 ≥6.5 mmol/L 或 ≤2.5 mmol/L → CRITICAL 级提醒主管医师，要求 30 分钟内确认闭环（依据幕3知识资产②）。
  - R2 DDI：华法林 + 阿司匹林联用 → HIGH 级出血风险提示，医师确认后方可继续（依据权威药物相互作用知识）。
  - R3 医保：阿莫西林/克拉维酸限「细菌感染诊断」支付提示（演示医保审核类规则）。
- **动作**：配置三规则（关联幕2字典、幕3知识）→ 建规则测试用例跑通过/不通过两例 → 影子模式观察 → 启用 → 规则校验页全量校验。
- **通过判据**：测试用例红绿正确；影子期不打扰临床只记录；启用后幕6真实触发。
- **体验评审重点**：配置完成后，让「非配置者」读这条规则——读不懂即印证 OPT-VIS-01（自然语言回显 + 流程图视图，§6.3）。
- **同步产出**：《试点准备手册》「规则配置」章（含 R1 从配置到医生收到提醒的全链示意图）；词条（影子模式、灰度、闭环、红线）。

### 幕5 · 路径引擎（CAP 临床路径）

- **目的**：路径模板建模到图形化阅读；**现场验证 PathwayGraphEditor（已有 React Flow 实现）对医生是否可读**。
- **角色**：呼吸科医生（临床牵头）、医务处质控员。
- **入口**：`/pathway/templates` 路径配置（含图形编辑器 `frontend/src/pages/tenant/PathwayGraphEditor.tsx`）。Controller：`PathwayEngine`。
- **真实数据**：CAP 社区获得性肺炎临床路径——节点：入院评估（CURB-65 评分）→ 经验性抗感染（关联 R3 药品）→ 48–72h 疗效评估 → 降阶梯/升级分支 → 出院评估（症状+影像标准）；里程碑：24h 内完成评估、48–72h 评估必达；变异类型：延迟出院、抗菌升级。
- **动作**：建模板（节点/边/里程碑）→ 图形视图阅读评审 → 发布模板。
- **通过判据**：路径发布可用；**呼吸科医生角色能在图上口述出整条路径**——说不出即登记 OPT-VIS-02 具体改进点。
- **同步产出**：《临床运行手册》「临床路径」章；词条（路径、节点、里程碑、变异、降阶梯）。

### 幕6 · 患者与临床运行（推荐引擎全链）⭐ 客户最痛

- **目的**：把「推荐引擎在哪里」一次性讲清楚：从患者建档到医生收到推荐卡的完整因果链。
- **角色**：检验技师（触发）、心内科/呼吸科医生（接收）、临床药师（DDI override 复核）、医务处质控员（观察）。
- **入口**：`/mpi` 患者主索引、`/pathway/patients` 患者路径、`/cdss/fatigue` 临床提醒治理、`/workflow/todos` 待办中心、`/notifications` 通知中心。Controller：`Mpi`、`ClinicalEvent`、`RealtimeCdsHook`、`RecommendationEngine`、`DiagnosisAssist`。
- **真实数据**：虚构患者「演练-张建国，男，64 岁」，诊断 ZD0456（CAP，经幕2映射）＋房颤史（华法林在用）。
- **动作**（一条因果链走到底，全程记 traceId）：
  1. MPI 建档 → 患者入 CAP 路径（幕5模板实例化）；
  2. 注入临床事件：检验回报「K001 = 6.8 mmol/L」→ 经幕2映射为 LOINC 2823-3 → 触发 R1 危急值规则 → 推荐卡推送主管医生 → 医生待办/通知中收到 → 30 分钟内确认闭环；
  3. 注入医嘱事件：阿司匹林处方 → 触发 R2 DDI → 医生选择「覆盖」并填理由（override 留痕）；
  4. 质控员与临床药师在提醒治理页看两条提醒的命中/确认/覆盖统计（药师重点复核 DDI override 理由是否充分）。
- **通过判据**：两条链路 traceId 全程可查；覆盖理由进审计；路径页可见患者当前所处节点。
- **体验评审重点**：走完后回答「推荐引擎在哪里？」——若答案分散在 4 个页面且无总览，即印证 **OPT-IA-01 + OPT-TRACE-01**（§6.3）必须做。
- **同步产出**：《临床运行手册》「提醒与推荐」章（以本幕真实链路为案例，一图贯穿）；词条（推荐卡、CDS、覆盖、闭环、疲劳治理）。

### 幕7 · 随访与质控评估

- **目的**：院后管理与质控闭环。
- **角色**：呼吸科医生、呼吸科护士（随访任务执行）、医务处质控员。
- **入口**：`/clinical/followup` 智能随访、评估指标库/评估结果页、`/qc/alerts` 质控预警、`/qc/dashboard` 院级质控驾驶舱。Controller：`FollowupEngine`、`EvaluationEngineCanonical`、`QualityDashboard`、`Rectification`、`ValueMetrics`。
- **真实数据**：CAP 出院后随访计划（7 天电话随访 + 30 天再入院观察 + 症状问卷）；质控指标：危急值 30 分钟闭环率、抗菌药物 48–72h 评估完成率。
- **动作**：建随访计划绑定幕6患者 → 生成任务 → 护士执行一次随访填报（顺带验证 NURSE 角色权限边界）；配置两指标 → 跑评估 → 看结果 → 触发一条质控预警 → 建整改任务 → 驾驶舱总览。
- **通过判据**：随访任务如期生成；指标计算结果与幕6演练事实一致（如闭环率 100%）；整改任务可闭环。
- **同步产出**：《质控改进手册》全骨架；词条（随访计划、指标、预警、整改、驾驶舱）。

### 幕8 · 配置包与发布治理

- **目的**：知识「打包出厂」的产品化通道，第二阶段批量分发的机制验证。
- **角色**：信息科管理员、医务处质控员（发布审批）。
- **入口**：`/config/packages` 配置包中心、`/config/releases` 发布治理。Controller：`PackageEngine`、`ReleaseGovernance`、`KnowledgeExport`、`Projection`、`SafetyWithdrawal`。
- **动作**：把幕2–5 成果（字典+知识+规则+路径）打成配置包 → 发布计划 → 灰度（仅呼吸科）→ 验证灰度边界（心内科不受影响）→ 全量 → 演示一次安全撤回；离线导出包 → 校验签名/摘要 →（模拟）院内导入。
- **通过判据**：灰度边界真实生效；撤回后规则停发；离线包导入对账一致。
- **同步产出**：《试点准备手册》「配置包与发布」章；词条（配置包、灰度、撤回、离线导出、对账）。

## §6 体验重构线（线C）——顶级医疗产品体验师的全方位梳理

### 6.1 体验北极星与五原则

北极星见 §0。五原则（新增/改造 UI 一律对照，沉淀进 [EXPERIENCE_CONTRACT.md](../../EXPERIENCE_CONTRACT.md)）：

1. **医院语言**：界面零技术黑话（glossary 是唯一词源），按钮动词用科室日常用语。
2. **任务导向**：用户带着任务来（「我要让系统提醒危急值」），不是带着引擎名来；导航与搜索按任务组织。
3. **配置即可读**：任何配置完成态必须能被「非配置者」读懂——自然语言回显 + 图形视图双轨。
4. **一图贯穿**：跨页面的因果链（事件→规则→推荐→反馈）必须有单页总览图。
5. **零迷路**：每页知道「我在哪、这页干嘛、下一步、出错找谁」；空状态必给第一步引导。

### 6.2 三层诊断框架与全页面审计

```
第一层 找得到（IA/可见性）：能力有没有入口？入口名字能不能猜到？
第二层 看得懂（语言/可视化）：进来后名词、状态、配置读不读得懂？
第三层 用得对（引导/防错/反馈）：知不知道下一步？错了有没有救？做完有没有确认感？
```

**全页面四问审计**（44 页逐页，随所在幕执行，结果入 §6.5 登记表）：
1. 外行 30 秒能否说出这页是干什么的？
2. 页内名词是否全部是医院语言（或有词条提示）？
3. 此刻「下一步动作」是否明显？
4. 出错/空白时用户是否知道怎么办？

每问 0–2 分，**≤4 分的页面必须出优化提案**。

**能力可见性审计**（一次性专项）：71 个后端 Controller ↔ 44 页面（双实测）建映射表，归档到本计划同目录 `capability-visibility-matrix.md`；每个无 UI 入口的能力标注：补入口 / 并入既有页 / 明确 API-only（写进第三方案例集）。推荐引擎已是第一个实锤。

## §8 演练收尾：134 清库重置（已实证流程）

演练数据验收归档后执行（**需用户当次点名授权**，破坏性）：

1. `pg_dump -Fc` 先落 `/tmp` 再 `mv` 入 `/zoesoft/medkernel/backups/post-drill-YYYYMMDD.dump`（backups 属主 medkernel，postgres 直写会 Permission denied）；
2. `systemctl stop medkernel`；
3. `sudo -u postgres psql -d medkernel`：`DROP SCHEMA public CASCADE; CREATE SCHEMA public; ALTER SCHEMA public OWNER TO medkernel; GRANT ALL ON SCHEMA public TO medkernel; GRANT ALL ON SCHEMA public TO public;`
4. `medkernel-deploy --jar <最新jar> --no-rollback --health-timeout 180`（Flyway 全量重迁）；
5. 校验：`SELECT COUNT(*) FROM flyway_schema_history WHERE success;`＝当时迁移总数（**勿用 MAX(version)，varchar 字典序会骗人**）+ health UP。

> 若 OPT-DEMO-01 演示场景包已实现，清库后可一键回灌演示包，134 变常备演示环境。

## §9 接力机制

- **状态唯一真相源**：`_HANDOFF.md` 增「演练与体验重构」工作线，格式：`幕N 状态（done/doing/blocked）｜证据目录｜下一步精确动作｜待用户决策项`。
- **PR 节奏**：每幕一 PR（指南+词条+小修复同 PR）；体验优化项每项独立 PR；全部走分支→CI→授权合并。
- **本计划即总纲**：剧本/提案表有变更随 PR 更新本文件，不另开计划文档。
- **用户决策点**（攒批问，不零碎打扰）：①每幕收尾的优化提案优先级确认；②P1 以上缺陷的修复时机；③清库授权；④第二阶段启动宣告。
