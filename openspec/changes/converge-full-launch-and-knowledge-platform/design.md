## Context

MedKernel 当前候选分支相对 `origin/main` 累积 460 个提交和 587 个变更文件，已经具备三产品空间、版本化资产、平台标准版本、机构生效版本、知识生产代表链路及 134 单机部署骨架，但尚无可信完整上线结论。已复现的阻塞包括前端严格校验失败、真实性库存未清零、五方言 V1 与规范模式不一致、35/34 入口口径冲突，以及发布制品未与完整验证结果绑定。

现有“离线交付”只导出机构生效清单坐标，条目缺少资产正文、依赖、来源和验证附件；导入通过本地证据 ID 回查，并要求来源发布已存在于接收端。因此它只能在同一实例恢复，不能把 134 的平台标准版本交付给断网、空数据库的医院。当前证据签名又把临时公钥随证据保存，能证明内容自洽，却不能证明发布者是平台权威源。现有院内部署包也未携带 PostgreSQL、Nginx 和必要 OS 包的离线依赖仓库，无法兑现“空白主机、无公网”的安装合同。

利益相关方包括平台医疗引擎运营员、平台管理员、有资质医学责任人、医院信息科、临床使用者、审计员和实施运维人员。用户要求按最优决策连续执行，不设置反复人工项目门禁；医疗内容审核、临床确认及 134 清库等不可替代的责任动作仍必须保留。

## Goals / Non-Goals

**Goals:**

- 保护当前成果并在独立工作区建立可重复、可追溯的干净 RC 基线。
- 用机器可验证的唯一总账证明 35 个入口及 `LAUNCH-01`～`LAUNCH-15`，禁止代表切片冒充完整功能。
- 让 134 成为当前平台知识权威宿主，同时允许未来迁移到其它服务器而不改变资产身份和医院信任关系。
- 交付可引导空医院实例的完整签名平台医疗资源包，在线和离线共用一套可信导入、激活和回滚语义。
- 在现有 13 类资产版本体系内生产全系统所需资源，覆盖 11 个知识分类、16 个医疗语义族、全专业代表资源及 S0～S40 场景依赖。
- 形成不可变院内软件包、空机安装器、备份恢复、监控和真实目标环境证据，使同一制品可重复部署到医院。
- 保持模型关闭、134 断开、图投影或第三方不可用时的 B0 主链和诚实降级。

**Non-Goals:**

- 不宣称收录世界上全部医学知识；完整性以 `PRODUCT_SCOPE` 定义的资源族、覆盖矩阵、运行消费者和持续更新能力为准。
- 不新增第 14 类医疗资产，也不让离线文件、搜索索引、图数据库、模型或对象存储成为业务权威源。
- 不以本次变更替换 Spring Boot、React、关系数据库、Flyway 或现有 `deploy/onprem` 技术栈。
- 首发不把当前开发型 Docker Compose 改造成生产编排，不在未做真实 smoke 前承诺所有 OS、CPU 架构和数据库组合。
- 不让平台包包含患者数据、医院凭据或院内运行结果，也不允许医院本地覆盖自动反写平台主源。
- 不自动执行医嘱、签署、支付、法定上报或设备控制。

## Decisions

### 1. 冻结输入锚点，在隔离分支形成 RC0 后保全进入主线

当前 `7217504ce82e1aa119c3402e3b5d054f9369e018` 只固化为 `sourceBaseCommit` 收敛输入锚点，不具备 RC 或可提升资格。所有实施在 `codex/launch-convergence` 独立 worktree 完成；先修复可复现 P0 并提交候选，再从该候选的全新干净检出建立 clean 基线。第一个全部规定门禁通过的完整 `candidateCommit` 才成为 RC0，清单同时保留输入锚点和候选提交的来源链。随后用成果保全 PR 合入 `main`；后续任务按小写集自动合并。

选择这一方案是因为它既保留 460 个提交的真实成果，又停止在巨型分支继续累积不可审查风险。备选“从 `origin/main` 逐片移植”会重复数周工作；“继续原分支直接加功能”会污染用户脏文件并放大假绿；“重写全部系统”不符合最快上线目标。

### 2. 自动回归替代中间人工项目门禁，最终只跑一次完整验收

自动回归分为提交级、主线级和 RC 级：提交级执行格式、类型、真实性、受影响测试和数据库生成检查；主线级执行 clean 后端全测、前端 `verify/build`、CLI/MCP、部署契约和库存清零；RC 级在独立临时栈执行全量 E2E、知识/资产、韧性和 `LAUNCH-01`～`LAUNCH-14` 就绪汇总。

最终候选只构建一次，JAR、前端、SBOM、迁移、manifest 和签名全部绑定同一 40 位提交哈希。只有 134 目标环境执行 `LAUNCH-15` 后，严格总账才允许 15 项全部 `PASSED`；任何 `UNKNOWN`、`SKIPPED`、重试掩盖或静态布尔自证都判失败。

### 3. 平台权威身份与宿主解耦

新增稳定 `authorityId` 表示平台知识权威，`t-1` 继续表示唯一平台主租户；每台实际发布服务器使用不同 `issuerInstanceId` 和独立发布密钥。医院的首次信任只能由已签名软件 manifest 固定 `authorityId` 与根指纹，或由独立认证通道一次性注入，禁止把与 `.mkp` 同介质携带的未知根作为首次使用即信任（TOFU）。同一 `authorityId` 同时只能有一个可签发的活动实例，迁移时先冻结旧实例，再通过数据库、原件、审计、包注册表、信任链和密钥设施交接激活新实例。

医院信任预置平台根证书和 `authorityId`，不信任固定 IP、主机名或包内任意公钥。签名私钥由 HSM/KMS 或等效受控设施保存，包记录 `keyId`、证书链、有效期和吊销信息；轮换由旧可信根签署新根。权威迁移的原子边界同时吊销或禁用旧 issuer 的发布密钥并授权新 issuer 密钥，旧 134 即使断网后从旧数据库快照恢复也不能产生医院可接受的新包。备选“134 IP 即权威身份”“包内临时公钥自签”和“只靠复制数据库后的 CAS 防双活”均拒绝。

### 4. 使用确定性完整 `.mkp` 包，而不是数据库 dump 或远程指针

默认平台交付是可引导空实例的完整快照。包包含规范化 `manifest.json`、13 类资产精确正文、稳定身份和版本、来源锚点与再分发许可、依赖 BOM、测试向量和结果、禁用/撤回条目、最低引擎和数据库模式版本、全文件 SM3 摘要、SM2 签名和信任链。离线文件只是运输容器，不成为业务版本或临床运行指针。

差量包只用于优化，并必须精确匹配 `fromDigest`；缺少历史链、摘要不符或撤回链不完整时，客户端必须回退完整包。数据库 dump 会耦合方言、租户和内部表结构，远程指针不能支持断网医院，因此均不采用。

### 5. 在线与离线统一进入隔离导入服务

HTTPS 拉取和人工上传介质都先进入受管隔离区。服务按顺序验证：包格式、权威信任、证书状态、全文件摘要、防重放、目标机构、许可、软件/模式兼容性、资产正文、精确依赖闭包及测试向量。验证只读取包文件，不依赖来源服务器、本地证据 ID 或本地已有来源发布。

通过后在事务暂存区物化资产身份、版本、正文、来源、依赖和包注册事实，重复包按权威 ID、发布 ID 和摘要幂等。真实文件流式下载、上传和在线拉取只作为传输适配器，统一执行大小、文件数、解压比、并发、幂等、权限和审计限制；现有只提交 `evidenceId` 的前后端旁路必须迁移。系统生成差异、冲突、影响和撤回传播预览；授权责任人确认后，以期望当前机构版本执行 CAS 原子切换并生成新的不可变机构生效版本。失败必须整体回滚，不留下半导入资产；历史回滚在医院本地复制精确清单生成更高修订，不依赖 134 在线。发布治理前端必须覆盖载入、空、正常、错误、无权限和降级六态。

### 6. 为 13 类资产提供统一传输合同和类型适配器

每种 `VersionedAssetType` 必须实现统一 `export/validate/materialize` 端口，输出规范正文、稳定身份、版本、哈希、依赖和来源引用。共用正文模型的类型复用通用适配器；具有独立领域表的类型使用小型专属适配器，但不得建立第二套版本或依赖体系。适配器登记必须覆盖全部 13 类，缺少任一类型时平台完整包不得发布。

### 7. 医疗资源工厂以覆盖矩阵驱动，不以数量或文件上传冒充完整

生产链固定为来源发现与授权、原件内容寻址留存、解析与引用锚点、新版/重复/冲突识别、B0 或模型候选、类型校验、依赖闭包、测试和影响分析、当前责任人审核、不可变资产发布、平台标准版本、运行消费、更新检测、替换、撤回和回滚。

唯一覆盖矩阵把 13 类资产、11 个知识分类、疾病与诊断等 16 个完整医疗语义族、全医疗专业领域、S0～S40、专病十阶段、第三方消费者及五种交付形态映射到来源、当前版本、依赖、质量结果、责任人、运行消费者和缺口。规则必须自包含完整条件树，路径必须自包含完整节点，不引入条件片段库、共享子路径、路径继承或循环嵌套。未获许可、来源失效、审核缺失或无正式消费者的资源只能保持待处理，不能进入平台标准版本。

原件、PDF、OCR 和解析中间产物首发使用 `/zoesoft/medkernel-data` 受管本地文件存储，数据库保存元数据、版本、审核和生效权威事实。暂不引入尚不存在的 S3/MinIO 适配器；未来可在现有存储端口下扩展而不改变业务合同。

### 8. 134 与医院首发复用强化后的单机 `deploy/onprem`

首发拓扑为 HTTPS 443 Nginx、静态前端、回环地址 Java 21 服务、PostgreSQL 权威库、受管资料盘、可选回环 Ollama 和可重建图投影。公网只开放 443，22 仅限运维来源，5432、18080、11434 不对公网开放。

首发支持 profile 固定为 openEuler 24.03 LTS x86_64 与 PostgreSQL 16 主版本。新增不可变软件包，包含后端 JAR、前端 dist、JRE21、唯一 V1、systemd/Nginx 模板、幂等 `preflight/install/upgrade/rollback/status`、备份恢复、验收脚本、manifest、摘要、签名、SBOM、可选已批准离线模型，以及签名的 openEuler 离线依赖仓库。软件 manifest 与支持矩阵锁定 PostgreSQL、Nginx 和全部必要 OS 包的精确版本、NEVRA、来源与摘要；安装期间禁止访问公网仓库。站点 overlay 只保存主机、CA、数据库、目录、机构和集成配置，不打包任何凭据。

134 在工程稳定后先部署为平台资源生产与发布环境。医院复用同一签名软件包和平台医疗资源包，只更换站点 overlay；首发正式承诺 openEuler 24.03 LTS x86_64、PostgreSQL 16、本机 Nginx 与受管本地资料盘，精确包组合由支持矩阵登记。其它数据库、OS、架构或包组合只有在真实 smoke 后才进入支持矩阵。

### 9. 备份和证据覆盖数据库、资料与发布信任链

清库前备份数据库、程序、配置、受管资料目录、包注册表、证书元数据和审计，签名私钥只按密钥设施的受控备份流程处理，不进入普通归档。备份必须有加密、保留策略、异机复制、失败告警和周期隔离恢复；应用只读展示真实 RPO/RTO 演练结果。

目标证据汇聚器必须直接检查文件存在并重算摘要，绑定主机、候选提交、制品摘要、run-id、时间和执行命令结果；证据目录不得包含凭据或患者明文。旧的“接收外部 JSON 并检查字符串形状”不能作为上线证明。

### 10. 医疗安全和降级是运行不变量，不是可跳过的项目流程

模型只生成有来源、有 AI 标识的候选；未审核内容不得进入临床。医疗动作仍须医师确认，高危事项逐条责任确认，禁止自动开嘱、支付、签署、上报和设备控制。模型、图、134 或第三方关闭时，医院保留最后一个已验证机构生效版本并返回 `B0`、`NOT_CONNECTED`、`NOT_SYNCED` 或 `MODEL_DISABLED`，不得伪造成功。

### 11. LAUNCH 缺口闭环与目标工具先在本地完成

机器总账把每个失败或缺证项分类为 `IMPLEMENTATION`、`TEST`、`DATA` 或 `ENVIRONMENT`。前三类仓库内可解决缺口必须自动进入“失败测试、最小实现、真实消费者与审计回读、重新归零”闭环；只有当前无法控制的现场资源才能进入待处理清单，且对应总账继续保持未通过。这一反馈循环是实施工作，不是人工中间门禁。

134 上只运行已经由本地和临时双实例栈验证的工具。单次破坏性确认状态机、确认后漂移失效、十段顺序编排、独立证据重算和 48～72 小时稳定观察器必须先有失败合同测试并在非目标环境通过；不得在 134 上边开发边执行。

## Risks / Trade-offs

- [巨型输入成果隐藏跨域回归] → 先将输入锚点与可提升候选分离，再做 clean 基线和机器总账；保全后只允许小写集，全量 E2E 使用独立数据库栈分片，禁止共享可变实例。
- [完整资源生产被误解为无限知识收集] → 以产品范围覆盖矩阵、正式消费者和持续更新闭环作为完成定义，不使用文件数量或分类名称计数。
- [来源许可不允许再分发] → 包按资源记录许可策略；不可再分发原文时只交付允许的结构化派生、引用坐标和校验信息，未满足许可不得发布。
- [签名根泄露或双活发布] → 私钥进入受控密钥设施，实例激活使用唯一约束和迁移冻结；支持吊销、轮换和旧根签署过渡。
- [13 类资产正文结构不一致] → 统一传输合同配合类型适配器，并以登记完整性测试阻止缺类型发布。
- [大型完整包占用磁盘和导入时间] → 内容寻址去重、流式摘要、事务批次和可选严格差量；完整包仍为恢复真相源。
- [134 单机故障] → 定时数据库与资料备份、异机复制、恢复演练；医院运行不依赖 134 在线，未来可迁移权威宿主。
- [空白服务器无公网依赖] → 只支持锁定的 openEuler 24.03 LTS x86_64 profile，把 PostgreSQL 16、Nginx 与必要 OS 包作为签名离线仓库纳入 manifest/SBOM，安装时禁止公网软件源。
- [首次信任根被同介质替换] → 根指纹只由已签名软件 manifest 或独立认证通道预置，禁止 TOFU，并在安装、轮换和导入时审计指纹。
- [旧 134 从快照恢复后形成签发分叉] → issuer 使用独立密钥，交接同时在 HSM/KMS 围栏旧 key，医院按交接序号拒绝旧 issuer 新包。
- [首发栈范围较窄] → 先交付真实可复用的 Linux x86_64/PostgreSQL 路线，其它组合通过五方言生成合同和现场真实 smoke 逐项纳入。
- [无中间人工门禁降低可见性] → 所有进度、失败和缺口实时进入机器总账，自动失败阻止合并，但不要求人员逐批批准。

## Migration Plan

1. 固化 `sourceBaseCommit` 输入锚点和本 OpenSpec；在隔离 worktree 修复基线并提交候选，再从候选的全新检出运行 clean 后端、前端、真实性、数据库和部署基线，全部通过后形成 RC0。
2. 先修复前端严格校验、真实性库存、五方言 V1 和 35/34 入口，再把生产构建、全 E2E、完整总账和同一 SHA 制品提升接入 CI/Release。
3. 通过成果保全 PR 将同一源码树纳入 `main`，确认远端主线和制品哈希后，后续任务从最新 `main` 分支化。
4. 由规范模式源新增平台权威、信任根、发布实例、包注册和导入作业事实，生成并验证五方言 V1；实现可信签发和完整包格式。
5. 按 13 类资产逐个完成适配器、导出、空库物化、依赖闭包和篡改/重放/不兼容测试；将旧同实例离线恢复入口迁移为统一文件导入服务，必要时保留受限兼容读取期。
6. 补齐医疗资源工厂和覆盖矩阵，在本地双实例环境生产平台基线、导出完整包，并由完全空医院实例离线导入、激活、升级和回滚。
7. 构建包含签名 openEuler 离线依赖仓库的不可变院内软件包和空机安装器，在隔离 openEuler 24.03 LTS x86_64/PostgreSQL 16 环境完成断网安装、B0、备份恢复和卸载/重装验证。
8. 工程候选就绪后，对 134 做只读预检；备份和隔离恢复完成后，在一次破坏性确认下清库并仅执行 V1，部署相同签名制品。
9. 在 134 生产并发布平台医疗资源基线，运行十段完整演练、双实例迁移、重启、二次恢复和 48～72 小时稳定观察。
10. 归档本次 run-id 脱敏证据，生成医院 site overlay 和交付包；医院以同一包完成空机安装、资源导入、接口 `NOT_CONNECTED` 基线及现场逐项联通。
